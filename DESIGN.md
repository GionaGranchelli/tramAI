# Aurora — Design Document
### A structured-first, observability-native AI workflow library for the JVM
**Version:** 0.2-draft  
**Author:** Design session — April 2026  
**Implementation language:** Kotlin  
**Framework policy:** Framework-agnostic core, optional Spring adapter  
**Serialization:** Jackson (with kotlin-module)

---

## 1. Problem Statement

### Situation
Backend engineers on the JVM are increasingly asked to integrate AI capabilities into existing applications. The tooling available is either Python-native (LangChain, LlamaIndex) or a direct port of Python idioms into Java (LangChain4j) — neither of which feels idiomatic to a Kotlin/Java engineer who thinks in types, interfaces, and coroutines.

### Complication
LangChain4j exists but inherits LangChain's mental model: chains, agents, and prompt templates as first-class abstractions. This model has known production problems — hard to test, hard to observe, leaky abstractions that expose model internals to application code. Structured outputs are an afterthought. Observability requires manual instrumentation. It is also Spring-centric, leaving Quarkus, Micronaut, and plain Java users as second-class consumers.

### Question
Can we build a JVM-native AI library where **typed interfaces are the only abstraction**, structured outputs are the default contract, and every AI interaction is automatically observable — with zero boilerplate?

### Answer
Yes. Aurora is that library.

## 2. Design Philosophy

Four principles, in priority order:

**1. Typed contracts over prompt engineering**  
Application code never manipulates raw prompt strings. Inputs are Kotlin data classes or Java POJOs. Outputs are Kotlin data classes or Java POJOs. The library owns the translation layer between JVM types and model I/O.

**2. Observable by default**  
Every AI call emits an OpenTelemetry span automatically, following the OTel GenAI semantic conventions. No configuration required if OTel is already on the classpath. Token usage, latency, retry count, and model identity are trace attributes, not log lines.

**3. Fail loudly, recover gracefully**  
Structured output parsing failures are not swallowed. They are retried with the validation error fed back to the model. After max retries, a typed exception is thrown with the full context of what failed and why.

**4. Boring to use, interesting to build**  
The consumer API surface is intentionally minimal. One annotation, one interface, one way to do things. Complexity lives inside the library, not in the application code.

**5. Kotlin-native, Java-friendly**  
The library is written in Kotlin and exposes idiomatic Kotlin APIs — coroutines, data classes, DSL builders, reified generics. Every public API also has a Java-callable entry point. Consumers on Java never hit a wall.

## 3. Core Abstraction

The single unit of Aurora is the **AI Operation** — an annotated Kotlin interface method.

```kotlin
@AiService
interface InvoiceAnalyzer {

    @Operation(
        prompt = "Analyze this invoice and extract line items with cost categories",
        model = "claude-sonnet-4-20250514"
    )
    suspend fun analyze(invoice: Invoice): InvoiceAnalysis

    @Operation(
        prompt = "Classify this expense by category and flag anomalies",
        model = "gpt-4o"
    )
    suspend fun classify(expense: ExpenseRecord): ExpenseClassification
}
```

Rules:
- Interface must be annotated with `@AiService`
- Each method must be annotated with `@Operation`
- Method parameters are serialized as structured context — multiple parameters are supported
- Return type determines behavior:
  - `String` → raw model output, no parsing
  - `Unit` → fire-and-forget
  - Any Kotlin data class or Java POJO → structured output with schema validation and retry
  - `suspend fun` → coroutine-native, non-blocking execution
  - Blocking variant available for Java consumers and non-coroutine codebases
- No implementation required — Aurora generates a proxy at startup

### Coroutine vs blocking dispatch

Aurora detects at proxy generation time whether a method is a `suspend fun`. If it is, the provider call is dispatched on a coroutine. If not, the call is blocking. Both signatures are valid — the interface author chooses per method.

```kotlin
// Coroutine consumer (Kotlin)
val analysis = analyzer.analyze(invoice)  // suspend, non-blocking

// Blocking consumer (Java or non-coroutine Kotlin)
InvoiceAnalysis analysis = analyzer.analyzeBlocking(invoice);
```

Blocking variants are auto-generated by Aurora as extension wrappers — the interface itself only declares the suspend version.

```
├── Aurora-observability/      # OTel integration, span emission, GenAI conventions

│   ├── Aurora-anthropic/      # Anthropic API provider
│   ├── Aurora-openai/         # OpenAI API provider
│   └── Aurora-ollama/         # Ollama local provider
├── Aurora-standalone/         # Zero-config entry point for plain JVM usage
├── Aurora-spring/             # Optional Spring Boot autoconfiguration adapter
├── Aurora-testing/            # Test utilities, mock provider, assertion helpers
└── Aurora-bom/                # Bill of materials for version management
```

### Dependency philosophy

`Aurora-core` has **zero runtime dependencies** beyond the Kotlin stdlib. Providers, observability, and framework adapters are all opt-in. A consumer who wants only the core structured output pipeline with no OTel and no Spring pays zero overhead for those modules.

### Standalone usage (no framework)

```kotlin
// Kotlin
val Aurora = Aurora {
    provider(AnthropicProvider(apiKey = System.getenv("ANTHROPIC_API_KEY")))
    defaultModel("claude-sonnet-4-20250514")
}

val analyzer = Aurora.create<InvoiceAnalyzer>()
val result = analyzer.analyze(invoice)
```

```java
// Java — same underlying object, Java-friendly builder
Aurora Aurora = Aurora.builder()
    .provider(new AnthropicProvider(System.getenv("ANTHROPIC_API_KEY")))
    .defaultModel("claude-sonnet-4-20250514")
    .build();

InvoiceAnalyzer analyzer = Aurora.create(InvoiceAnalyzer.class);
InvoiceAnalysis result = analyzer.analyzeBlocking(invoice);
```

### Spring Boot usage (optional adapter)

```kotlin
// application.yml drives everything — no @Bean required
@Service
class BillingService(private val analyzer: InvoiceAnalyzer) {
    suspend fun process(invoice: Invoice) = analyzer.analyze(invoice)
}
```

```yaml
Aurora:
  default-model: claude-sonnet-4-20250514
  providers:
    anthropic:
      api-key: ${ANTHROPIC_API_KEY}
    ollama:
      base-url: http://localhost:11434
```

The Spring adapter scans for `@AiService` interfaces and registers proxies as beans. Everything else is identical to standalone usage.

## 6. Structured Output Pipeline

This is the core intellectual work of the library. The pipeline for any non-String return type:

```
1. SCHEMA GENERATION
   Java return type → JSON Schema
   Uses Jackson SchemaGenerator + custom annotations for descriptions and constraints
   Schema is cached per method at startup, not generated per call

2. PROMPT CONSTRUCTION
   User prompt template + input serialization + schema injection
   Schema is injected as a system instruction: "Respond ONLY with valid JSON matching this schema"
   Input objects are serialized to a readable JSON block in the user turn

3. MODEL CALL
   Request dispatched to ModelProvider
   Raw text response captured

4. RESPONSE PARSING
   Raw text → JSON extraction (handles markdown fences, preamble)
   JSON → Jackson deserialization into return type
   Bean Validation (JSR-380) applied if validator on classpath

5. VALIDATION FEEDBACK LOOP (if parsing fails)
   Validation error message appended to conversation
   "Your previous response failed validation: [error]. Please correct it."
   Re-sent to model, up to @Operation(maxRetries = N)
   Default: 2 retries

6. FAILURE
   After maxRetries exhausted: throw AuroraStructuredOutputException
   Exception contains: original prompt, last raw response, validation error, attempt count
```

### Schema annotations

```kotlin
data class SpendAnalysis(
    @AiDescription("Total spend in USD, always positive")
    val totalSpend: Double,

    @AiDescription("List of cost reduction recommendations, ordered by impact")
    @AiMinItems(1)
    val recommendations: List<Recommendation>,

    @AiDescription("Confidence score between 0.0 and 1.0")
    @AiRange(min = 0.0, max = 1.0)
    val confidence: Double
)
```

`@AiDescription` is injected into the JSON schema as the `description` field — models use this to understand intent. Jackson's kotlin-module handles data class serialization natively — no additional configuration required.

## 7. Prompt Rendering

Prompts support simple template syntax bound to method parameter names:

```kotlin
@Operation(prompt = "Analyze the spend data for tenant {{tenantId}} and return optimization strategies")
suspend fun analyze(tenantId: String, data: SpendRecord): SpendAnalysis
```

Template variables map to parameter names via Kotlin reflection. Complex objects are serialized to JSON inline. Kotlin's `@param:` annotation target is supported for parameter-level annotations.

For multi-turn or context-heavy prompts, a `@SystemPrompt` annotation at the interface level sets a persistent system instruction:

```kotlin
@AiService
@SystemPrompt("You are a Datadog cost optimization expert. Be concise and actionable.")
interface SpendAnalyzer {
    // ...
}
```

## 8. Observability Layer

### OTel GenAI Semantic Conventions

Every provider call wraps in a span named `ai.{operation_name}` with the following attributes, following the [OTel GenAI semantic conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/):

| Attribute | Value |
|---|---|
| `gen_ai.system` | `anthropic` / `openai` / `ollama` |
| `gen_ai.request.model` | Model identifier string |
| `gen_ai.request.max_tokens` | Configured max tokens |
| `gen_ai.response.model` | Actual model used (may differ from requested) |
| `gen_ai.usage.input_tokens` | Token count from response metadata |
| `gen_ai.usage.output_tokens` | Token count from response metadata |
| `Aurora.operation.interface` | Fully qualified interface name |
| `Aurora.operation.method` | Method name |
| `Aurora.retry.attempt` | Current attempt number (0-indexed) |
| `Aurora.structured.parse_success` | Boolean — did structured parsing succeed |

### Span events

Structured output failures are recorded as span events, not exceptions:

```
Event: Aurora.parse.failure
  Aurora.raw_response: "<raw model output>"
  Aurora.validation_error: "Field 'totalSpend' must be positive"
  Aurora.attempt: 1
```

### Auto-detection

If `opentelemetry-api` is on the classpath, Aurora registers its `ObservabilityInterceptor` automatically. No `@EnableAuroraObservability` annotation required. If OTel is absent, a no-op tracer is used.

## 9. Provider Model

### Provider interface

```kotlin
interface ModelProvider {
    suspend fun complete(request: ModelRequest): ModelResponse
    fun supportsStructuredOutput(): Boolean = false
    fun providerId(): String = this::class.simpleName ?: "unknown"
}

data class ModelRequest(
    val model: String,
    val messages: List<Message>,
    val maxTokens: Int,
    val temperature: Double?,
    val responseSchema: JsonSchema?   // null for raw String returns
)

data class ModelResponse(
    val content: String,
    val inputTokens: Int,
    val outputTokens: Int,
    val modelUsed: String,
    val finishReason: FinishReason
)
```

The provider interface is a `suspend fun` — all network I/O is coroutine-native. Blocking adapters are generated for Java consumers.

### Provider resolution

When `@Operation` specifies a model string, Aurora resolves the provider by prefix:

- `claude-*` → AnthropicProvider
- `gpt-*` / `o1-*` / `o3-*` → OpenAiProvider
- `llama*` / `mistral*` / `gemma*` → OllamaProvider
- Explicit override via `@Operation(provider = "ollama")`

### Native structured output

If the provider supports native structured output (OpenAI's `response_format`, Anthropic's tool-use trick), Aurora uses it. If not, Aurora falls back to the schema-in-prompt pipeline. `supportsStructuredOutput()` controls this routing.

## 10. Retry and Error Handling

### Retry hierarchy

Three distinct retry scenarios, each configurable independently:

**Structured output retry** — model returned unparseable or invalid JSON  
Default: 2 retries. Feeds validation error back to model.

**Provider retry** — transient HTTP errors (429, 503, network timeout)  
Default: 3 retries with exponential backoff. Configurable via `@Operation(providerRetries = N)`.

**No retry** — authentication errors, invalid model name, context length exceeded  
These throw immediately as `AuroraConfigurationException`.

### Exception hierarchy

```
AuroraException (base, unchecked)
├── AuroraStructuredOutputException   — exhausted retries on parsing
├── AuroraProviderException           — provider returned unrecoverable error
├── AuroraConfigurationException      — misconfiguration detected at startup
└── AuroraTimeoutException            — call exceeded configured timeout
```

All exceptions include the full request context for debugging.

## 11. Framework Integration

### Design principle

Aurora has no framework dependency in its core. Framework adapters are thin modules that wire Aurora's standalone API into the framework's dependency injection and configuration systems. The core logic is identical regardless of which adapter — or none — is used.

### Spring Boot adapter (Aurora-spring)

`AuroraAutoConfiguration` activates when `Aurora-spring` is on the classpath:
- Scans for `@AiService` interfaces in the application packages
- Registers generated proxies as Spring beans — injectable with `@Autowired` or constructor injection
- Reads provider configuration from `application.yml` under the `Aurora.*` namespace
- Detects OTel on the classpath and enables observability automatically

```kotlin
// Spring Boot consumer — identical to standalone, Spring provides the proxy
@Service
class BillingService(private val analyzer: InvoiceAnalyzer) {
    suspend fun process(invoice: Invoice) = analyzer.analyze(invoice)
}
```

### Quarkus and Micronaut

Not shipped in v1. The standalone API works in both frameworks — consumers instantiate Aurora manually and register it as a CDI bean or Micronaut singleton. Community adapters can follow the `Aurora-spring` module as a template.

### Plain JVM / CLI / Azure Functions

```kotlin
fun main() {
    val Aurora = Aurora {
        provider(OllamaProvider(baseUrl = "http://localhost:11434"))
    }
    val analyzer = Aurora.create<InvoiceAnalyzer>()
    runBlocking { println(analyzer.analyze(sampleInvoice())) }
}
```

No framework, no classpath scanning, no magic. Aurora is a library, not a container.

## 12. Testing Support

### Aurora-testing module

Provides a `MockAiProvider` that returns canned responses without network calls:

```kotlin
@Test
fun `analyze returns structured result`() = runTest {
    val Aurora = Aurora {
        provider(MockAiProvider {
            onMethod("analyze") respondWith """
                { "totalSpend": 1200.50, "confidence": 0.95, "recommendations": [] }
            """
        })
    }

    val analyzer = Aurora.create<InvoiceAnalyzer>()
    val result = analyzer.analyze(testInvoice())

    assertThat(result.totalSpend).isEqualTo(1200.50)
}
```

No HTTP stubbing, no Mockito. The mock lives inside the test, scoped to that test only.

### Spring Boot testing

```kotlin
@SpringBootTest
class InvoiceAnalyzerTest {

    @Autowired lateinit var analyzer: InvoiceAnalyzer

    @MockAiResponse(method = "analyze", returns = """
        { "totalSpend": 1200.50, "confidence": 0.95, "recommendations": [] }
    """)
    @Test
    fun `analyze returns typed result`() = runTest {
        val result = analyzer.analyze(testInvoice())
        assertThat(result.totalSpend).isEqualTo(1200.50)
    }
}
```

### Assertion helpers

```kotlin
AuroraAssertions.assertThat(analyzer)
    .whenCalled("analyze")
    .emittedSpanWithAttribute("gen_ai.system", "anthropic")
    .andRetried(0)
    .andParsedSuccessfully()
```

## 13. What Aurora Is Not (v1 Scope Boundaries)

The following are explicitly out of scope for v1:

- **RAG / vector store integration** — retrieval-augmented generation is a separate problem
- **Agent loops** — multi-step autonomous agents with tool selection
- **Streaming responses** — token-by-token streaming (planned v2)
- **Function / tool calling** — model-initiated tool calls (planned v2)
- **Conversation memory** — multi-turn stateful conversations (planned v2)
- **Prompt management UI** — no dashboard, no prompt registry
- **Fine-tuning** — no training data management

Each of these is a deliberate cut. v1 must be shippable and trustworthy before adding surface area.

## 15. Differentiation Summary

| Concern | LangChain4j | Aurora |
|---|---|---|
| Primary abstraction | Chain / Agent | Typed interface method |
| Implementation language | Java | Kotlin |
| Async model | Blocking / Reactor | Coroutines native, blocking adapters for Java |
| Structured output | Add-on | Default contract |
| Serialization | Jackson / custom | Jackson with kotlin-module |
| Observability | Manual | Automatic, OTel GenAI conventions |
| Framework coupling | Spring-centric | Framework-agnostic core, Spring as optional adapter |
| Testing | Mock HTTP | `MockAiProvider` DSL, no network |
| Retry on parse failure | Not built-in | Built-in, with validation feedback loop |
| Error transparency | Variable | Typed sealed exception hierarchy |
| Java compatibility | First-class | First-class, explicit Java entry points |

## 16. Open Questions

1. **Proxy mechanism** — KSP compile-time generation vs JDK Dynamic Proxy at runtime. KSP is faster and GraalVM-friendly but adds build complexity. Start with JDK proxy, migrate to KSP if native image demand emerges.

2. **Jackson schema generation** — Jackson's built-in `JsonSchemaGenerator` vs a custom one that understands `@AiDescription` and Kotlin nullability natively. Custom gives better model output quality and is the right long-term answer. Build custom from M2.

3. **Kotlin nullability in schema** — Nullable types (`String?`) should map to schema properties without `required`. Non-nullable types should be `required`. Jackson kotlin-module handles this but needs explicit validation.

4. **Model string resolution** — prefix-based routing (`claude-*` → Anthropic) is simple but fragile as model naming evolves. A provider registry with explicit model registration is cleaner. Decide before M3.

5. **GraalVM native image** — suspend function proxies and reflection at runtime are painful for native compilation. Design with it in mind — no unregistered reflection. Explicit GraalVM metadata in each module. Defer native image support as a stated goal, not a blocker.

6. **Coroutine dispatcher** — provider HTTP calls should run on `Dispatchers.IO`. Make this configurable per provider so consumers with custom dispatcher setups are not surprised.
