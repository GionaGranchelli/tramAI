# ADR-012: Keep `tramai-standalone` Minimal and Make Observability an Explicit Opt-In Module

- Status: accepted
- Date: 2026-04-18

## Context

Tramai wants two things at the same time:

- a strong observability story
- a minimal framework-free runtime with limited transitive dependency surface

Those goals are compatible only if automatic observability is understood as "auto-enable when the observability module is present" rather than "always bundled transitively by the standalone artifact."

If `tramai-standalone` pulls `tramai-observability` by default, then users who do not want OpenTelemetry dependencies still receive them transitively. That weakens the existing module philosophy that observability is opt-in, even if the runtime path is a no-op when OTel APIs are absent.

## Decision

Tramai will keep `tramai-standalone` minimal and make observability an explicit opt-in module.

The packaging model is:

- `tramai-standalone` composes the minimal non-framework runtime
- `tramai-observability` is a separate optional module
- observability auto-enables when the observability module and required OTel APIs are present
- observability is not a mandatory transitive dependency of the minimal standalone runtime

## Consequences

Positive:

- keeps the standalone artifact honest and lightweight
- preserves the claim that observability is optional at the dependency level
- reduces transitive dependency footprint for users who do not want OTel

Negative:

- users who want tracing must add one more artifact
- documentation must explain the difference between minimal standalone and standalone-plus-observability setups

## Implementation Guidance

- Define `tramai-standalone` as the composition of `tramai-core`, `tramai-engine`, and `tramai-structured`.
- Keep observability integration thin and attachable around the engine execution path.
- If Tramai later wants a batteries-included entry point, introduce a separate convenience artifact rather than making `tramai-standalone` heavier by default.
