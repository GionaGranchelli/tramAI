# ADR-016: Keep Runtime Proxies and Ship Explicit Native-Image Proxy Metadata Support

- Status: accepted
- Date: 2026-04-20

## Context

Tramai v1 uses JDK dynamic proxies for `@AiService` interfaces. Native-image support pressures that decision because GraalVM needs explicit proxy metadata for interfaces that will be proxied at runtime.

One possible response would be to replace runtime proxying with generated implementations immediately. That would push the codebase toward KSP or another compile-time generation path before the rest of the production-hardening work is complete.

The repository already documents in ADR-002 that code generation may become attractive later if native image support becomes important enough. The open question is whether native-image support now requires that larger architectural change.

## Decision

Tramai will keep runtime JDK proxies in v1 and provide an explicit native-image metadata path instead of switching to generated implementations immediately.

That path is:

- applications list their `@AiService` interfaces
- Tramai generates `proxy-config.json` entries for those interfaces
- native-image builds include that generated metadata

## Consequences

Positive:

- preserves the current runtime architecture
- gives native-image users a documented and testable path now
- avoids forcing KSP and generated code into the core delivery path prematurely

Negative:

- users still need to declare which service interfaces belong in the native image
- full AOT automation remains future work

## Implementation Guidance

- Keep the metadata generator small and dependency-light.
- Validate that supplied types are actual `@AiService` interfaces.
- Document the generated file location and expected GraalVM proxy-config shape.
