# ADR-021: Supported Headless Workflow Cancellation Control Boundary & Transactional Evidence Coupling

- **Status:** accepted
- **Date:** 2026-11-15
- **Task:** TASK-0.7.7m
- **Governing Epics:** Epic 0.7.6 ([EPIC-0.7.6-AUTH-RUNTIME-CONTROL.md](../roadmap/0.7.0/EPIC-0.7.6-AUTH-RUNTIME-CONTROL.md)), Epic 0.7.7 ([EPIC-0.7.7-SUSPENDED-RUN-CANCELLATION.md](../roadmap/0.7.0/EPIC-0.7.7-SUSPENDED-RUN-CANCELLATION.md))
- **Related:** ADR-018, ADR-019, ADR-020, [DEPENDENCY-BASELINE-0.7.7.md](../roadmap/0.7.7/DEPENDENCY-BASELINE-0.7.7.md)

## 1. Context

Milestone D7-F ([TASK-0.7.7l-D7-F-INTEGRATION-CLOSURE.md](../roadmap/0.7.7/TASK-0.7.7l-D7-F-INTEGRATION-CLOSURE.md)) delivered durable workflow cancellation mechanics in `WorkflowCheckpointStore`, admission fencing across outbound effect families (E1–E9, E11), and recovery lease fencing (E10).

However, the whole-repository security surface inventory conducted in 0.7.6h revealed that cancellation lacked an authenticated, authorized, typed REST command controller in the supported library starter (`tramai-spring-boot-starter-sovereign-ops-rest`). The only HTTP endpoint triggering cancellation was `DELETE /workflows/{name}/runs/{id}` in `tramai-server`, an unauthenticated, unsupported prototype.

The absence of an authenticated, authorized, typed cancellation control endpoint in `tramai-spring-boot-starter-sovereign-ops-rest` was designated an **explicit release blocker for Epic 0.7.7** ([DEPENDENCY-BASELINE-0.7.7.md](../roadmap/0.7.7/DEPENDENCY-BASELINE-0.7.7.md) §5.2).

## 2. Decision

We introduce a supported, headless, authenticated, and authorized workflow cancellation command in `tramai-spring-boot-starter-sovereign-ops-rest`:

`POST /tramai/sovereign/workflows/{workflowName}/runs/{runId}/cancel`

The implementation enforces the following architectural principles:

### 2.1 Three-Level Authorization Model
1. **Level 1 (Identity & Authentication):** Handled by the existing `@Order(1)` stateless `SecurityFilterChain` in `OperatorAuthenticationAutoConfiguration` protecting `/tramai/sovereign/**`. Requires valid RS256 JWT tokens. Produces `OperatorAuthority` carrying verified `(issuer, subject)`, capabilities, and approver roles. Unauthenticated callers receive HTTP 401.
2. **Level 2 (Operator Capability):** Enforces dedicated `OperatorCapability.CANCEL_WORKFLOW` (wire name `cancel-workflow`). Evaluated **before any workflow checkpoint lookup** (existence-blind). Callers lacking this capability receive HTTP 403 `MISSING_CAPABILITY` and an `AUTHORIZATION_REFUSAL` audit outbox record is durably emitted without disclosing run existence.
3. **Level 3 (Target-Scoped Authorization):** Enforces server-controlled `OperatorWorkflowCancellationPolicy`, mapping target workflow names to required roles. Evaluated **before any workflow checkpoint lookup** (existence-blind). If the workflow policy is unconfigured or the operator's verified roles do not intersect the requirement, the command fails closed with HTTP 403 (`WORKFLOW_POLICY_UNAVAILABLE` or `ROLE_NOT_PERMITTED`) and records a target-attributed refusal audit record without disclosing run existence. The authorization scope is workflow-wide administrative authority based on target `workflowName` (with optional wildcard `*`); an operator holding the required role for a given workflow is authorized to cancel any run of that workflow. TramAI does not implement individual per-run user ACLs or run-level ownership checks at this boundary; multi-tenant or fine-grained per-user run authorization belongs to application layers upstream of the operator control plane.

### 2.2 Typed Preconditions & Idempotency
1. Request body `CancelWorkflowRunRequest` requires `expectedRevision: Long >= 0` and non-blank `reason: String`. Missing, negative, or invalid values fail closed with HTTP 400 Bad Request.
2. Revision fencing: Mutation executes a CAS against `revision = expectedRevision` and `lifecycle_status IS NULL`.
3. Stale revision: If the current revision does not match `expectedRevision` and the run is not cancelled, the command fails with HTTP 409 `STALE`, disclosing `expectedRevision` and `currentRevision` without mutating state or outbox.
4. Idempotency: If the run is already cancelled, the store returns the existing `WorkflowLifecycleState`. No duplicate audit records or revision increments occur.

### 2.3 Strict Transactional Coupling (Atomicity)
Cancellation state mutation in `tramai_workflow_checkpoints` and evidence emission in `audit_outbox` must be committed **within a single database transaction**:
1. Single JDBC connection with `autoCommit = false`.
2. Checkpoint row is verified for existence and matching revision.
3. Outbox record is inserted in `PREPARED` state.
4. Checkpoint row is updated via CAS (`cancelInConnection`), incrementing `revision = revision + 1` and recording terminal cancellation metadata.
5. Outbox record is updated to `PENDING` with the resulting lifecycle status (`CANCELLED` or `CANCELLED_UNCERTAIN`), next revision, and actor attribution.
6. Connection commits. If any step fails or an exception occurs, the transaction rolls back completely.

### 2.4 Honest In-Flight Accounting
Consistent with Invariant I1 of Epic 0.7.7:
- Runs cancelled with `admission_sequence == 0` transition to `WorkflowLifecycleStatus.CANCELLED`.
- Runs cancelled with `admission_sequence > 0` transition to `WorkflowLifecycleStatus.CANCELLED_UNCERTAIN`.
- TramAI does not claim that cancellation compensates or reverses already-admitted external side effects.

---

## 3. Consequences

### Positive
- Resolves the Epic 0.7.7 release blocker by delivering a supported, secure, headless cancellation API.
- Fully reuses the 0.7.6 OIDC security chain, canonical `ActorIdentityDigest`, and transactional outbox.
- Atomically couples workflow lifecycle state with immutable audit evidence.
- Preserves single-linearization-point guarantees and idempotent retry semantics.

### Negative / Trade-offs
- Sovereign ops persistence requires JDBC backing (`tramai-spring-boot-starter-sovereign-persistence-jdbc`) to execute the single-transaction atomic CAS and outbox insertion. Non-JDBC checkpoint backends fail closed at startup.
- Multi-tenant applications must enforce run-level authorization before delegating to the workflow-level cancellation endpoint.
