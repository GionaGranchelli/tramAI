# ADR-014: Keep Tool Calling Engine-Owned and Provider-Portable

- Status: accepted
- Date: 2026-04-18

## Context

Tool calling is an important next capability for Tramai, but provider APIs differ significantly in how they expose it. If Tramai allows provider-native tool payloads to become the main application-facing contract, the product will lose the explicit, provider-portable execution model it has worked to establish.

At the same time, a tool-calling design that ignores provider-native capabilities entirely would throw away useful optimizations and compatibility paths.

## Decision

Tramai will keep tool calling engine-owned and provider-portable.

The design boundary is:

- consumers register tools through an Tramai-owned abstraction
- the engine owns the tool orchestration loop
- providers may use native tool capabilities internally when available
- provider-specific tool payloads are not the primary consumer-facing API

## Consequences

Positive:

- preserves Tramai's product identity as a stable JVM abstraction rather than a thin wrapper over provider APIs
- keeps tool execution testable and auditable inside the Tramai runtime model
- leaves room for native-provider optimizations without exposing them as required concepts

Negative:

- Tramai must maintain an abstraction layer over uneven provider capabilities
- some provider-native expressiveness may be deferred or normalized away in the first milestone

## Implementation Guidance

- Keep tool registration explicit and runtime-configurable.
- Treat tool execution as application-owned logic invoked by engine-owned orchestration.
- Do not let tool-calling design collapse into a generic agent framework in the first milestone.
