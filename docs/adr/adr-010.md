# ADR-010: Use an Explicit Provider Registry Instead of Model-Prefix Routing

- Status: accepted
- Date: 2026-04-18

## Context

Provider resolution by model-name prefix is simple to explain, but it is operationally fragile.

Tramai already identified this risk in the design open questions:

- model names evolve over time
- providers add new model families and aliases
- local and hosted deployments may use arbitrary model names
- fallback rules based on naming conventions become harder to reason about as providers proliferate

Because provider routing sits on a core execution path, a brittle resolution scheme would create ongoing maintenance cost and surprising behavior for users.

## Decision

Tramai will use an explicit provider registry from the start instead of relying on model-prefix routing as the primary routing mechanism.

The registry must support:

- explicit provider registration
- explicit model-to-provider registration
- explicit provider selection on an operation when needed
- deterministic resolution errors when no provider can satisfy the requested model or provider

Model-name heuristics may still exist as optional convenience helpers, but they must not be the core routing contract.

## Consequences

Positive:

- more predictable provider resolution
- less maintenance churn as model catalogs change
- better support for custom, local, aliased, or enterprise-managed model names
- clearer extension path for future providers

Negative:

- slightly more upfront configuration or registration logic
- registry behavior must be documented clearly

## Implementation Guidance

- Keep provider registry rules explicit and testable.
- Prefer deterministic lookup and clear startup or execution-time errors over silent fallback.
- Do not make Ollama the implicit fallback for unknown model names.
- If convenience helpers exist, treat them as sugar on top of explicit registration rather than as hidden routing policy.
