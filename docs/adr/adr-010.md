# ADR-010: Multimodal Content Model

- Status: accepted
- Date: 2026-05-14
- Related spec: [SPEC-019 Multimodal](../specs/spec-019-multimodal.md)

---

## Context

Golem, an autonomous agent framework built on TramAI, needed native multimodal support for browser screenshots, document images, and generated images. TramAI's existing message model had `content: String` (text-only) with a `contentParts: List<ContentPart>?` escape hatch that already supported `ImagePart` for raw bytes.

The requirements were:
1. Support images passed by URL (not just raw bytes)
2. Support images returned by tool results
3. Provider capability introspection
4. Image detail control
5. Image-aware token estimates

## Decisions

### 1. Keep `contentParts` parallel field, NOT `content: List<MessageContent>`

**Decision:** The existing `content: String` + `contentParts: List<ContentPart>?` parallel field pattern was retained rather than changing `content` to `List<ContentPart>` as originally proposed.

**Rationale:** Changing `content` to a list would break every message construction site (~50+ across the codebase). The parallel field approach is backward-compatible, requires a single-line `content = ""` when using contentParts, and works identically at the provider serialization level. The performance cost is negligible.

### 2. `ImageUrlContent` as a sealed variant, NOT `ImageData` sealed interface

**Decision:** Added `ImageUrlContent(url, mimeType?)` directly to the `ContentPart` sealed interface, rather than creating a separate `ImageData` type with `Base64` and `Url` subclasses.

**Rationale:** The existing `ImagePart` already stores raw bytes (not base64), so a separate `ImageData.Base64` type would be redundant. A single `ImageUrlContent` variant is simpler: one data class, one serialization branch per provider. Providers that support URLs directly (OpenAI, Gemini) pass them through; providers that require base64 download the URL to bytes and treat it identically to `ImagePart`.

### 3. URL download at provider serialization time, NOT at message construction time

**Decision:** URL-to-bytes resolution happens inside each provider's `messageToMap()` method, not in the Message constructor or a factory. Shared utility: `ImageDownloader`.

**Rationale:** Deferred execution means the download only happens when the message is actually sent to a provider that needs base64. OpenAI and Gemini never download — they pass the URL directly. This avoids unnecessary network I/O and lets each provider decide its own format.

### 4. Default-false capability enum, NOT abstract interface method

**Decision:** `supportsCapability()` has a default implementation returning `false`. Providers that support VISION override it.

**Rationale:** Adding a new method to `ModelProvider` is a source-breaking change for implementors. A default implementation maintains full backward compatibility while allowing providers to opt in. The engine checks the capability before every image-containing request.

### 5. Additive `contentParts` on `ToolResult.Success`, NOT a separate content type

**Decision:** `ToolResult.Success` gained an optional `contentParts: List<ContentPart>?` field (default `null`), rather than creating a standalone `ToolResultContent` sealed variant.

**Rationale:** All existing `ToolResult.Success(value)` calls compile unchanged. The engine checks for contentParts and, when present, constructs a `Message(role=TOOL)` with both the text value and image content parts. This is the minimal change that closes the gap — tools can return images without any API changes to callers.

### 6. Rough token estimation, NOT provider-precise accounting

**Decision:** `Message.estimateImageTokens()` uses a fixed 170 tokens per image (OpenAI's formula for 1 tile at 224px). UsageMetrics gained transparent default-zero fields.

**Rationale:** Precise token counting requires image dimension parsing (PNG/JPEG headers), provider-specific tile formulas (OpenAI splits images into 224px tiles; Anthropic uses a different formula), and actual token reports from provider responses. A rough estimate is sufficient for token budget management and TokenJuice compression decisions. Precise counts are available from provider responses.

## Consequences

### Positive
- All existing code compiles and runs unchanged
- No migration needed for existing users
- All 7 providers gain URL-based image support with one change each
- Provider capability checks prevent confusing runtime errors
- Images in tool results work without API surface changes
- Token estimates are available without network calls

### Negative
- URL downloads add latency for Anthropic/Ollama/Bedrock users (mitigated by the 20MB/10s/30s safety limits)
- Token estimates are approximate, not precise (acceptable for budget management)
- `contentParts` and `content` mutual exclusivity requires callers to blank `content` (mild ergonomic friction, documented)

### Neutral
- `ImageDownloader` adds a URL parsing dependency to tramai-core (stdlib only, no new jars)
- 3 production method visibility changes (private→internal for testability)
