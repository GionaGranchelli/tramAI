# ADR-015: Limit Streaming Failover to Startup Before the First Emitted Token

- Status: accepted
- Date: 2026-04-19

## Context

Tramai now supports explicit fallback routing, provider-health circuit breaking, and streaming execution. That creates a new resilience question: should the engine attempt to resume or switch providers after a stream has already emitted user-visible tokens?

At first glance, mid-stream failover sounds attractive, but it is not a transport-only problem. Once tokens have been emitted, the library would need a correctness rule for how to combine partial output from one provider with fresh output from another provider. Different providers may continue a sentence differently, restart a response, or reinterpret the prompt context in incompatible ways.

Because Tramai is a typed, backend-oriented library, silent output splicing is worse than an explicit terminal failure. The API should not pretend that two partial provider streams can always be merged into one trustworthy response.

## Decision

Tramai will allow streaming failover only before the first token is emitted.

The engine behavior is therefore:

- if stream startup fails before any token is emitted and the failure is retryable, the engine may try the next configured fallback route
- once any token has been emitted to the consumer, Tramai will not switch providers for that stream
- after user-visible output has begun, failures remain terminal for that stream and are surfaced explicitly

## Consequences

Positive:

- preserves correctness over cosmetic availability
- keeps streaming semantics auditable and unsurprising
- aligns streaming resilience with Tramai's explicit-failure philosophy

Negative:

- some recoverable late-stream failures still terminate the stream
- applications that want custom continuation behavior must build it above Tramai with application-specific rules

## Implementation Guidance

- Keep startup-only streaming failover in `tramai-engine`.
- Record resilience and routing events so operators can see when startup failover happened.
- Do not introduce hidden prompt replay or output-merging behavior in provider modules.
