# ADR-018: Separate Security Enforcement from SaaS Platform Concerns

- **Status:** accepted
- **Date:** 2026-06-01
- **Supersedes:** None
- **Related:** ADR-005 (framework-agnostic core), ADR-012 (minimal standalone), ADR-017 (orchestration)

---

## Context

TramAI is evolving from a typed AI integration library into a sovereign agent runtime for JVM enterprises. The current module structure (ADR-005, ADR-012, ADR-017) correctly separates:

- `tramai-core` — contracts, annotations, SPI
- `tramai-engine` — dispatch, routing, retry
- `tramai-structured` — schema generation, validation
- `tramai-orchestration` — workflow DSL, checkpoint, resume
- `tramai-standalone` — minimal composition module

The roadmap now requires adding security enforcement capabilities: policy engine, approval gates, audit emission, model registry, and sovereign deployment profiles.

A parallel concern is the `tramai-platform` module (experimental), which currently contains multi-tenant SaaS features: RBAC, API key management, secret management, dashboard, and billing.

These two concerns — **security enforcement** and **SaaS platform** — must be separated.

---

## Decision

**Security enforcement capabilities are embedded in the application runtime. They work without a control plane, without a dashboard, and without network connectivity.**

**SaaS platform capabilities remain in `tramai-platform` and are optional. They require a running server, network access, and centralized state.**

### Module assignments

| Capability | Module | Works embedded? | Works without dashboard? |
|------------|--------|-----------------|--------------------------|
| Policy SPI | `tramai-security` | Yes | Yes |
| Tool authorization | `tramai-security` | Yes | Yes |
| Data classification | `tramai-security` | Yes | Yes |
| Provider routing policy | `tramai-security` | Yes | Yes |
| Approval gates | `tramai-security` | Yes | Yes |
| Audit emission | `tramai-security` | Yes | Yes |
| Model registry (local) | `tramai-security` | Yes | Yes |
| Sovereign profile aggregator | `tramai-sovereign` | Yes | Yes |
| Offline bundle | `tramai-sovereign` | Yes | Yes |
| SBOM / provenance | Build process | Yes | Yes |
| RBAC (centralized) | `tramai-platform` | No | No |
| API key management | `tramai-platform` | No | No |
| SaaS dashboard | `tramai-platform` | No | No |
| Billing | `tramai-platform` | No | No |
| Multi-tenant isolation | `tramai-platform` | No | No |

### Module structure (Phase 1)

```
tramai-core        → SPI contracts, shared enums, PolicyContext, PolicyDecision
tramai-engine      → mandatory enforcement hooks (calls PolicyEngine, never bypassed)
tramai-security    → policy + approval + audit + model registry (single artifact)
tramai-sovereign   → dependency aggregator + offline deployment profile
```

`tramai-sovereign` in Phase 1 is an aggregator skeleton. It becomes functionally sovereign in Phase 2 with bundles, model verification, and zero-egress evidence.

Separate artifacts (`tramai-policy`, `tramai-approval`, `tramai-audit`) are extracted later if independent adoption demands them (e.g., a consumer that needs policy without audit).

### Principle

> A regulated enterprise must be able to deploy TramAI inside a Spring Boot application, in an air-gapped environment, with full policy enforcement and audit capability — without installing a SaaS platform.

---

## Consequences

### Enforcement Points

`tramai-engine` invokes policy hooks at mandatory enforcement points. Skipping a hook is not possible through any code path. Absence of a policy module in secure mode causes fail-closed behavior. A legacy-permissive mode must be explicitly configured, not accidentally inherited.

**Mandatory enforcement points:**

1. **Before provider resolution** — classification check, model allowlist
2. **Before provider invocation** — provider policy, egress check
3. **Before fallback** — fallback provider must also satisfy policy
4. **Before tool exposure to model** — tool allowlist
5. **Before tool execution** — permission check, risk level, approval gate, egress check
6. **Before tool result reinjection** — result filtering, DLP
7. **Before response return** — output DLP, field-level policy
8. **Before workflow resume** — policy version check, state validation

Each point is a mandatory call to `PolicyEngine.evaluate(context)`. The engine cannot be bypassed — it is invoked from `TramaiEngine` internals, not from optional interceptor chains.

### Positive

- **No platform dependency for security.** Policy enforcement, approval gates, and audit emission work in any Spring Boot application with zero external services.
- **Cleaner attack surface.** Platform features that require network access, centralized state, and user management are isolated from the core security runtime.
- **Easier validation.** The embedded security runtime can be tested in isolation without standing up a platform.
- **Faster enterprise adoption.** Organizations can pilot TramAI with security controls before committing to a platform deployment.

### Negative

- **Module count increases.** One new module (`tramai-security`) plus `tramai-sovereign` as an aggregator.
- **Dual configuration surface.** Local model registry (file-based, offline) and centralized model registry (API, platform) must coexist.
- **Approval state management.** Human approval gates require some form of state management even in embedded mode. This must be pluggable (in-memory for dev/test, persistent for production).

### Staged Migration to Secure-by-Default

Secure mode must not break existing TramAI consumers on upgrade.

| Version | Behavior |
|---------|----------|
| 0.3.x | Existing behavior unchanged |
| 0.4.x security preview | `tramai-security` opt-in; warning logged when absent |
| `tramai-sovereign` profile | Always secure by default |
| 1.0 Enterprise | Secure-by-default documented as a breaking change |
| Compatibility path | Explicit `LEGACY_PERMISSIVE`, deprecated over time |

### Mitigations

- New modules follow existing conventions: `tramai-core` defines SPIs, implementation modules are optional.
- `tramai-sovereign` composes policy + approval + audit + model registry into a single dependency for sovereign deployments.
- Approval state is abstracted behind an SPI so embedded and platform deployments share the same contract.
- The platform can layer centralized governance on top of embedded enforcement without modifying the enforcement modules.

---

## Alternatives Considered

### A: Add security to `tramai-platform` only

**Rejected.** Would require a running platform server for basic security controls. Violates the "works embedded" requirement. A Spring Boot app in an air-gapped environment would have no policy enforcement.

### B: Add security to `tramai-engine`

**Rejected.** `tramai-engine` owns orchestration and retry. Adding policy enforcement there would couple security to the dispatch loop, making it harder to test and reason about independently.

### C: Add security to `tramai-core`

**Rejected.** `tramai-core` is SPI definitions, annotations, and models. Policy enforcement is an implementation concern. Core should remain dependency-light and focused on contracts.

### D: Merge policy, approval, and audit into one module

**Accepted for Phase 1.** A single `tramai-security` artifact reduces packaging complexity for the first release. Internal package separation (policy/approval/audit/model) preserves conceptual boundaries. Separate artifacts are extracted later if independent adoption demands them (e.g., a consumer that needs policy enforcement without audit). `tramai-sovereign` acts as a dependency aggregator.

---

## Verification

- [ ] Policy enforcement works in a Spring Boot test without `tramai-platform` on the classpath
- [ ] Approval gates work with an in-memory approval store
- [ ] Audit events are emitted and queryable without external services
- [ ] `tramai-sovereign` bundles policy + approval + audit + model registry as a single dependency
- [ ] `tramai-platform` can layer centralized governance on top of embedded enforcement
