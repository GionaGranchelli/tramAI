# ADR-009: Keep Retry Orchestration in tramai-engine and Structured Analysis in tramai-structured

- Status: accepted
- Date: 2026-04-18

## Context

The boundary between `tramai-engine` and `tramai-structured` is one of the most sensitive seams in Tramai's design.

Tramai needs both:

- engine-level ownership of operation orchestration, retry policy, and terminal failure behavior
- structured-output ownership of schema generation, response extraction, deserialization, and validation assessment

If parsing rules, validation logic, or schema-specific decisions leak into `tramai-engine`, the module boundary becomes brittle and the structured pipeline stops being a replaceable subsystem. If retry policy leaks into `tramai-structured`, the engine loses control of execution semantics.

## Decision

Tramai will keep retry orchestration in `tramai-engine` and structured-output analysis in `tramai-structured`.

The boundary works as follows:

- `tramai-engine` owns retry policy, attempt counting, retry limits, and terminal exception behavior
- `tramai-structured` owns schema generation, raw response extraction, deserialization, and validation assessment
- `tramai-structured` returns a result object that describes structured-output success or failure and includes enough failure detail for the engine to decide the next step
- `tramai-engine` decides whether to continue, retry with feedback, or fail
- `tramai-engine` must not embed parsing or validation logic
- `tramai-structured` must not decide retry policy

## Consequences

Positive:

- preserves a clean module boundary
- keeps retry semantics consistent across engine execution paths
- allows structured-output behavior to evolve without spreading parsing logic through the engine

Negative:

- the result contract between modules must be designed carefully
- failure information needs to be rich enough for retries without overexposing structured internals

## Implementation Guidance

- Prefer a boundary type name broader than `ValidationResult` if it also represents parse and extraction failures.
- A name such as `StructuredOutputResult` is likely more accurate than a validation-only name.
- The engine should consume that result as an orchestration input, not as a parsing API surface.
