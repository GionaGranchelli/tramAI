| 12 | MEDIUM | Implementation Feasibility | SPEC-016a | **Shutdown hook CAS guard re-arming in `start()` can race.** `TramaiWorker.start()` sets `shutdownStarted.set(false)` at line 210 (TramaiWorker.kt). | 13 | MEDIUM | Edge Cases | SPEC-016a | **What happens when the shutdown hook fires after `close()` has already completed?** `close()` calls `runBlocking { shutdown() }` (line 266-268). `shutdown()` sets `shutdownStarted.compareAndSet(false, true)` at line 233 — on success, proceeds. On the second call (from the hook after close()), CAS returns false and `shutdown()` returns immediately (line 234: `return`). This is correct behavior. But a dangerous edge: if `close()` is called from within the shutdown hook thread, the CAS guard prevents the hook's own call to `shutdown()` from entering, but `close()` calls `runBlocking { shutdown() }` which acquires `shutdownStarted` first — fine. However, if `close()` is called from a coroutine running on `Dispatchers.Default` and the hook tries `runBlocking(Dispatchers.IO)`, and all IO dispatcher threads are blocked by Default threads waiting for IO — deadlock possible if not using `Dispatchers.IO.limitedParallelism()`. The spec's use of `Dispatchers.IO` mitigates this but doesn't eliminate the theoretical deadlock under extreme thread starvation. |

## Overall Assessment

**IMPLEMENTABLE WITH MINOR CHANGES**

Both specs are fundamentally sound and implementable, but each has contradictions and gaps that must be resolved before implementation.

### SPEC-021 — Chat Memory v1.1

**Issues to resolve before implementation:**
1. Correct the self-contradiction between Section 4.1 (no ProviderCallResult changes) and Section 6 (ProviderCallResult modifications). **Follow Section 4.1.**
2. Resolve the module placement contradiction: Section 4.3 says `tramai-memory-store` (new module), Section 6 says `tramai-memory`. **Follow Section 4.3 — create `tramai-memory-store`.**
3. Clarify that the engine already calls `chatMemory.add()` directly — this is not a pattern change, just a data change in what messages are passed.
4. Add edge case validation: `require(maxTokens > 0)` in TokenAwareChatMemory.
5. Add AC for conversation eviction in TokenAwareChatMemory.
6. Specify serialization strategy for ChatMemoryStore implementations.
7. Add error handling strategy for PersistentChatMemory when store operations fail.
8. Update MemoryInterceptor.kt KDoc to reflect v1.1 capabilities.

**Overall:** The tool-call memory (TASK-093) is the simplest change — just modify the `chatMemory.add()` call in `executeRaw()` and `executeStructured()` to pass `effectiveMessages.drop(history.size)` instead of `originalMessages.filter { USER } + assistantMessage`. The structured output retry path already only persists on `StructuredOutputResult.Success`, so no change needed there.

### SPEC-016a — Distributed Execution Remaining

**Issues to resolve before implementation:**
1. Store the shutdown hook Thread reference and remove it in `shutdown()` to prevent double-registration on restart cycles.
2. Guard `ModHashPartitionStrategy` against empty `activeWorkers` list.
3. Add explicit AC for shutdown hook/idempotency.
4. Specify logging framework for `LoggingTramaiWorkerObserver`.
5. Add shutdown hook test.

**Overall:** All three remaining work items (shutdown hook, partition strategy extraction, observer events) are straightforward refactors against existing code. The shutdown hook CAS guard already exists; the partition extraction is a mechanical interface/class extraction; the observer events follow the established pattern in `OpenTelemetryWorkflowObserver.kt`.

### Priority Recommendation

1. **SPEC-021 TASK-093 (Tool-call memory)** — 2-line change in `executeRaw()` (TramaiEngine.kt:572-577), zero new classes. Highest impact per unit effort.
2. **SPEC-016a TASK-099 (Shutdown hook)** — Already battle-tested via `close()` → `shutdown()` path. Adding the hook is a thread registration.
3. **SPEC-021 TASK-094 (TokenAwareChatMemory)** — New class but well-scoped.
4. **SPEC-016a TASK-100 (Partition strategy extraction)** — Mechanical extraction, high testability.
5. **SPEC-016a TASK-101 (Observability completion)** — Follows established OTel pattern exactly.
6. **SPEC-021 TASK-095-097 (Persistence)** — Requires new module creation.
