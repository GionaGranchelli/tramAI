# 0.7.4b1 / G1a — Option A: governed identity as reserved PolicyContext attributes

**Base:** `6e1d4a1e8cbab8f5561f1cd372be9d4efb995938` (`release/0.7.0`).
**Branch:** `task/0.7.4b1-g1a-option-a-reserved-identity-attributes`.
**Predecessor:** PR #517 (the ABI findings that made the typed carrier impossible on this line).
**Change class:** `runtime-behaviour`. **No public API change** — verified below.

## 1. What this does

Makes the canonical `GovernedRunIdentity` reach the authoritative `PolicyEngine.evaluate(PolicyContext)`
path from the Spring AI XR1 boundary, **without** adding a property to `PolicyContext`.

The typed carrier is not available here: `PolicyContext` is `stable`, and adding a property breaks
compiled Kotlin consumers through the synthetic default-arguments constructor and `copy` — measured
with a control run, and recorded in `0.7.4b1-G1A-ABI-FINDINGS.md`. Reclassifying the module is an owner
decision this slice does not take.

So the identity travels as reserved `identity.*` keys in the **existing** `attributes` field, which is
the mechanism this repository already uses and documents for exactly this class of problem: 0.7.1d's
`RuntimeEvidenceAttribution` states that a typed identity field "would change that public ABI", and
carries the same five keys with the same atomic rule.

- **Binding** — `GovernedToolCallback.contextFor()` populates the deployment tuple from
  `BoundaryContext.identity`. The run id is *not* duplicated into the keys: it is `workflowRunId`, which
  `PolicyContextBuilder` and 0.7.1d already treat as the single canonical run identifier, and which the
  boundary already set from `identity.runId`.
- **Validation** — `DefaultPolicyEngine.evaluate` validates the tuple **before the
  enforcement-point branch**, so no enforcement point is reachable with an ambiguous identity. It calls
  the existing `RuntimeEvidenceAttribution.validate`: zero keys is legacy, a partial tuple is corruption,
  a complete tuple without the canonical run id is refused. Rejecting is fail-closed, and the boundary
  already converts an evaluation failure into a refusal with no execution.

## 2. Evidence — the red→green pair

The carriage suite captures **the actual `PolicyContext` the evaluator received**, by wrapping the real
`DefaultPolicyEngine` rather than reimplementing or stubbing it. A test that inspected the boundary's
inputs, or built its own context, would pass while the carriage was broken.

| Run | Suite | Result |
|---|---|---|
| Before the binding | `GovernedIdentityCarriageTest` | **2 of 5 FAILED** — exactly the two that assert the identity reached the evaluator |
| Before the binding | others in the same suite | passed — consistent: they assert run id, correlation and actor, which were already carried |
| After the binding | `GovernedIdentityCarriageTest` | 5/5, 0 failures |
| After the binding | `GovernedIdentityValidationTest` | 7/7, 0 failures |
| After the binding | pre-existing XR1 + security suites | `GovernanceBoundaryTest` 7, `AdversarialDiscriminatorTest` 7, `EvidenceIntegrityTest` 4, `FrameworkDispatchTest` 2, plus the security governance/evidence suites — all 0 failures |

The failure is therefore *specific*: it names the missing transport rather than failing blanket, and the
same assertions pass once the transport exists. Raw excerpts are in `evidence/0.7.4b1-option-a/`.

The validation suite's discriminator is the legacy/partial pair: an implementation that validates nothing
passes legacy and fails partial; one that rejects everything passes partial and fails legacy. Neither can
pass both by accident. A near-miss key (`identity.workload` instead of `identity.workloadId`) is covered
too, so a renamed key reads as an incomplete tuple rather than as identity.

## 4. What this does NOT establish

- **A caller-supplied key is not authenticated workload identity.** The boundary binds the tuple from the
  identity it was wired with, and the evaluator refuses an incomplete or run-less tuple — but nothing here
  authenticates *who* wrote the keys. Any caller that constructs a `PolicyContext` can set them. This
  slice proves **carriage and validation**, not authenticity, and the difference is not a formality: making
  the keys unforgeable is external-runtime registration work (G2), not this.
- **The key literals are duplicated.** `RuntimeEvidenceAttribution.metadataKeys` is `internal` to
  `tramai-security` and this boundary is a separate module, so the five literals cannot be imported. The
  duplication is guarded by a test asserting the evaluator receives all five, so a rename fails a test
  instead of silently downgrading a governed context to a legacy one. A shared public constant would remove
  it and would also be an API change this slice must not make.
- **Validation lives in the authoritative engine.** `DefaultPolicyEngine` validates; another `PolicyEngine`
  implementation would have to do the same. The invariant is "one authoritative evaluator", and a
  hypothetical second implementation is out of this slice's scope rather than covered by it.
- **Approval continuation, tool-permission evidence attribution (G1b), external-runtime provenance (G2),
  provider-routing evidence (G4) and any evidence-schema change are not addressed here.**

## 5. Unresolved, and next

- Whether the `preview` `api-migrations.yml` mechanism authorises the equivalent **typed** change. Untested;
  decisive if the typed carrier is ever preferred, and it also bears on G2, whose target types are in
  preview modules. This is experiment 1 from the ABI findings.
- Whether the evaluator's validation should also reject a *complete* tuple whose deployment identity
  contradicts a registered workload. That needs an authoritative registration store (0.7.1c) and is a
  substitution check, not a completeness check — deliberately not invented here.
