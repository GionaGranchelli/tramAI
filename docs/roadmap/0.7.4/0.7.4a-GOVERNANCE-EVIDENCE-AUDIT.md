## 5. 0.7.4b contract proposal — smallest compatible changes

Each item is traceable to a source-level gap above or to an existing authoritative contract. Where a smaller
option exists, it is named and rejected with the reason.

**G1 — the evaluator's input must accept the identity, and the tool path must carry it into evidence.**

What already exists, and what does not:

- *Implemented* — `RuntimeEvidenceAttribution` (`tramai-security/.../evidence/RuntimeEvidenceAttribution.kt:22-79`,
  0.7.1d, delivered work): five reserved metadata keys `identity.workloadId`, `identity.configurationId`,
  `identity.configurationVersion`, `identity.environmentId`, `identity.deploymentId`; `workflowRunId` is the single
  canonical run identifier and is deliberately **not** duplicated in metadata (`:13-16`); `merge()` overlays
  framework-owned attribution so caller metadata cannot shadow identity (`:40-49`); `validate()` is atomic — zero
  keys is valid legacy evidence, a partial tuple is corruption, a full tuple without a non-blank run id is rejected
  (`:55-73`); and callers must overlay **before** the payload digest so identity participates in the digest (`:37-38`).
  Staying stringly-typed is a documented decision: a typed field would change the public `runtime-evidence.v1` ABI
  and couple `tramai-security` to the core identity model (`:6-11`).
- *Missing* — the evaluator cannot receive the tuple at all: `PolicyContext` has no field for it
  (`PolicyContext.kt:17-44`), and the XR1 boundary holds the identity and drops it at that boundary
  (`GovernedToolCallback:108-117`). Separately, the tool-evidence path does not overlay the reserved keys, so even a
  context that carried them would not reach `tool.permission` records.

*Proposal:* add **one nullable, defaulted** `governedRunIdentity: GovernedRunIdentity? = null` to `PolicyContext`,
reusing the existing type; and have the tool-evidence path overlay the reserved keys through the existing
`RuntimeEvidenceAttribution.merge` **before** the digest is computed. This **extends** the 0.7.1d contract; it
introduces no second identity representation.
*Rejected smaller option:* encoding identity in `attributes: Map<String, String>`. Rejected because a stringly-typed
side channel is exactly the silent substitution the invariants forbid — the reserved keys exist so that attribution
is validated atomically rather than hoped for.
*Migration:* the defaulted parameter keeps all nine existing `PolicyContext` construction sites compiling, but
`PolicyContext` uses `@JvmOverloads`, so the generated overload set changes and the **API-compatibility and
binary-compatibility checks must pass**. Evidence written before the overlay carries zero reserved keys, which
`validate()` accepts as legacy.

**G2 — evidence must be able to say which declared boundary enforced, and how strongly.**

A producer identity cannot simply be made configurable. `source.component` is pinned to a **registered per-family
constant** in three coupled places: the exporter writes it (`ToolPermissionRuntimeEvidenceExporter.kt:73-76`),
`RuntimeEvidenceBundleWriter.EXPECTED_SOURCE_COMPONENTS` declares the permitted value per event type
(`:354-361` — `tool.permission` → `"policy-engine"`), `RuntimeEvidenceContractValidator.validateSourceComponent()`
rejects any mismatch (`:98-107`), and `computeToolPermissionPayloadDigest()` folds `sourceComponent` and
`sourceModule` into the canonical digest (`:105-112`). Changing the exporter alone would therefore be rejected by
the validator *and* silently change every payload digest.

That pinning is correct, not incidental: a `tool.permission` record reports the **policy engine's decision**, and
the engine is genuinely its producer. What the current model cannot express is the *other* fact — **which declared
boundary enforced that decision, and how strongly**.

*Proposal:* use the extension point the evidence contract already documents — per-family-validated **reserved
metadata keys** (`RuntimeEvidenceAttribution`'s stated mechanism: "an allowlisted, per-family-validated metadata
extension point", `RuntimeEvidenceAttribution.kt:6-11`). Add reserved keys for the declared boundary identity and
its enforcement strength, extend `ALLOWED_METADATA_KEYS["tool.permission"]` and the contract validator's per-family
rules accordingly, and overlay before the digest so they participate in it like identity does.
`source.component` stays `"policy-engine"`.
*Why not schema fields:* the checkpoint defers exact names and public API stability to the 0.7.4 evidence work
(`:61-70`) and does not require a new field. A reserved-key extension reuses an implemented, validated mechanism
instead of changing the public `runtime-evidence.v1` ABI — the smaller compatible change.

**How enforcement strength stays authoritative (corrected).** Strength must not be arbitrary adapter metadata, and
it must not be the evaluator's exclusive author — that would defeat XR1, whose purpose is to prove TramAI can
*prevent* an operation at an external boundary without claiming control of the host runtime. **Authorizing and
enforcing are different facts.** The correct basis is a **registered boundary plus its verified enforcement
contract**: the boundary is registered (the same allowlist discipline as `source.component`), and its strength
claim is backed by evidence that the boundary actually prevented the operation — which is exactly what the XR1
prevention proofs establish for the declared Spring AI boundary. An unregistered or unproven boundary may at most
report `OBSERVED`. Nothing in this rule lets an adapter promote itself, because registration and the prevention
proof are not adapter-owned.

**G3 — state the authorization/completion asymmetry normatively.**
The boundary records ALLOW **before** the effect (`GovernedToolCallback:78-85`), so an ALLOW record attests
authorization and never completion. Nothing states this, and the merged comment at
`BoundaryEvidenceRecorder.kt:78-79` mis-describes the exporter's failure mode.
*Proposal:* documentation only — correct the comment and state the asymmetry in the evidence schema's contract.
**An ALLOW record proves authorization, not successful execution.** That is the complete statement. No completion
mechanism is added or implied: the XR1 demonstration's invocation ledger shows execution *within that
demonstration* and is **not** a general production completion authority, so it cannot be cited as one. Inventing a
completion event would create a second authority over a fact the system does not currently attest.
*Traceable to:* the verified gap above plus the checkpoint invariant `observed != enforced`.

**G4 — an evidence family with no producer must be declared, not assumed.**
`provider.route` is exported, validated and tested but never emitted in production (T5).
*Proposal:* either wire it at the routing decision site, or mark it in the evidence contract as
**not currently produced** so no reader treats its absence as an absence of routing events.
*Traceable to:* T5, and to the invariant "missing or stale evidence cannot be reported as a successful
current control".

**Explicitly not proposed:** no new policy engine, no adapter SDK, no dashboard work, no schema-wide redesign,
no regulatory conformance claim (EU AI Act, ISO 42001) — the invariants forbid asserting those from evidence
alone, and this audit makes none.

## 6. Implementation dependency order

Ordered by dependency, not preference. Each step is blocked on the one above it.

1. **Correct the mis-describing comment** (`BoundaryEvidenceRecorder.kt:78-79`). Independent, trivial, no gate impact.
2. **G1a — `PolicyContext` accepts the tuple.** Touches a public type; requires the API-compatibility and
   binary-compatibility gates. Must not be bundled with a gate or analyzer change.
3. **G1b — the tool-evidence path overlays the reserved `identity.*` keys** via the existing
   `RuntimeEvidenceAttribution.merge`, before the digest. Depends on 2 for the identity to be available, and on
   nothing else.
4. **G2 — register the boundary and carry its enforcement strength as reserved metadata keys**, with the per-family
   allowlist and the contract validator extended to match, and the digest consequence handled explicitly. Reuses the
   same extension point as step 3, changes no ABI, and is what makes the strength claim checkable rather than
   asserted.
5. **G4 — declare or wire `provider.route`.**
6. **Freeze the 0.7.4b schema** only after 2–5 are demonstrable at a single tree, per the checkpoint's Exit clause.

Steps 1 is a prerequisite, not part of 0.7.4b. **The approval-carriage item is not a 0.7.4b prerequisite:** it is
open (`TASK-0.7.1e…:276-280`) against the *approval* creation paths, and XR1 defers approval continuation
entirely, so nothing in steps 2–4 depends on it. It must be resolved before 0.7.1 closes, not before 0.7.4b starts.

## Addendum — corrections after review

The reviewer of PR #516 identified four substantive errors and one counting error. All five are accepted; the
affected sections above are corrected, and the superseded statements are withdrawn here rather than silently
reworded.

**W1 — G2 assumed a configurable producer identity and overlooked an implemented contract. WITHDRAWN.**
The first version proposed letting the emitting component supply `source.component` and putting the module into
`source.module`. That conflicts with three existing mechanisms — `EXPECTED_SOURCE_COMPONENTS`
(`RuntimeEvidenceBundleWriter.kt:354-361`), `validateSourceComponent()`
(`RuntimeEvidenceContractValidator.kt:98-107`, which would **reject** the change) and
`computeToolPermissionPayloadDigest()` (`ToolPermissionRuntimeEvidenceExporter.kt:105-112`, which folds both values
into the canonical digest so every existing payload digest would change). The auditor had read the digest function
and did not connect it to the proposal. §5 G2 is rewritten to extend the documented reserved-metadata extension
point instead, changing no ABI.

**W2 — G2 conflated authorization with enforcement, defeating XR1's purpose. WITHDRAWN.**
The first version reserved `AUTHORITATIVE` to the evaluator's own emission path. That is wrong: the evaluator
authorizes, the boundary enforces, and the checkpoint exists precisely to prove TramAI can **prevent** an operation
at an external boundary without claiming control of the host runtime. The corrected rule derives strength from a
**registered boundary plus its verified enforcement contract** — backed by prevention evidence, not by a producer's
identity and not by adapter metadata.

**W3 — G1 understated existing identity-attribution infrastructure. CORRECTED.**
The first version presented the identity representation as absent. `RuntimeEvidenceAttribution` (0.7.1d,
implemented) already provides five reserved `identity.*` keys with atomic validation and digest participation. §5
G1 now separates what is implemented (the validated evidence representation) from what is missing (propagation
through `PolicyContext` and the tool-evidence path), so that 0.7.4b extends the existing contract.

**W4 — 0.7.1d was described as unimplemented. WITHDRAWN.**
The report inferred "unimplemented contract" from `GovernedRunIdentity`'s KDoc. The repository records 0.7.1d as
**implemented and green** (`TASK-0.7.1d-RUN-ATTRIBUTION.md:125`), and `RuntimeEvidenceAttribution` is its delivered
artifact. The `PolicyContext` gap remains genuine and verified; it is a distinct gap, not evidence about 0.7.1d.
The approval-carriage item is likewise no longer presented as a 0.7.4b prerequisite (§6) — it is open against the
approval paths, which XR1 defers entirely.

**W5 — counting error. CORRECTED.** The coverage matrix has **ten** rows, not eleven. (The identity-row wording
raised in the second review is addressed as W9.)

**W6 — "no inventoried path populates the reserved identity keys" was wrong. WITHDRAWN.**
`governance.decision` already does exactly this: `GovernanceDecisionEvidence.toRuntimeEvidenceRecord` (`:70-93`)
builds the attribution from the typed identity (`:75`), validates it atomically against the canonical run id
(`:76`), writes the run id as `workflowRunId` (`:80`), overlays the reserved keys via `merge` (`:91`) and folds the
attribution into the payload digest (`:89`, `:108`). §2 now names it as the worked example and restricts the gap to
the tool-permission and policy-decision paths.
