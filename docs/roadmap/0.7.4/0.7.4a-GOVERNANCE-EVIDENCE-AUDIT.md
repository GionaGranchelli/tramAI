## 5. 0.7.4b contract proposal — smallest compatible changes

Each item is traceable to a source-level gap above or to an existing authoritative contract. Where a smaller
option exists, it is named and rejected with the reason.

**G1 — the evaluator's input must accept the identity that already exists.**
`PolicyContext` carries no workload/configuration/deployment/environment identity (§2, `PolicyContext.kt:17-44`),
while the tuple is canonical elsewhere and its KDoc assigns propagation to candidate **0.7.1d**
(`GovernedRunIdentity.kt:10-16`). The XR1 boundary holds the tuple and cannot pass it (`GovernedToolCallback:108-117`).
*Proposal:* add **one nullable, defaulted** `governedRunIdentity: GovernedRunIdentity? = null` to `PolicyContext` —
reusing the existing type, introducing no new identity model.
*Rejected smaller option:* encoding it in `attributes: Map<String, String>`. Rejected because stringly-typed
identity is exactly the silent substitution the invariants forbid, and because evidence metadata is filtered by
allowlist, so it would not survive into evidence anyway.
*Migration:* defaulted `null` keeps every existing construction site (9, §2 of the inventory) compiling; because
`PolicyContext` uses `@JvmOverloads`, the change alters the generated overload set and **must pass the
API-compatibility gate and its binary-compatibility check** before merge.

**G2 — evidence must be able to say who produced it, and how strongly.**
`ToolPermissionRuntimeEvidenceExporter.kt:74` hard-codes `source.component = "policy-engine"` and puts
`policyVersion` into `source.module`; the 5-key allowlist (`:21-27`) excludes any integration key. A record
therefore cannot identify an external runtime, and the checkpoint's four strength concepts exist only in the XR1
example.
*Proposal:* (a) the emitting component supplies `source.component` rather than a constant, and
`source.module` carries the module, not the policy version; (b) `RuntimeEvidenceRecord` gains
`enforcementStrength` with the checkpoint's four values.
*Design rule (not an addition):* strength must be **derived from the emitting component's own declaration and
recorded by the governance path**, never supplied by an adapter. An adapter may at most request
`INSTRUMENTED`; only the evaluator's own emit path may write `AUTHORITATIVE`. This is what keeps
"external frameworks never become governance authorities" true once the field exists.
*Migration:* `enforcementStrength` needs a default for existing records; the `runtime-evidence.v1` schema
version is bumped only if the field is required. Prefer optional + documented default.

**G3 — state the authorization/completion asymmetry normatively.**
The boundary records ALLOW **before** the effect (`GovernedToolCallback:78-85`), so an ALLOW record attests
authorization and never completion. Nothing states this, and the merged comment at
`BoundaryEvidenceRecorder.kt:78-79` mis-describes the exporter's failure mode.
*Proposal:* documentation only — correct the comment and state the asymmetry in the evidence schema's
contract. No mechanism is added: "did it run" is answered by outcome/ledger observation, and inventing a
completion event would duplicate an authority that already exists.
*Traceable to:* the verified gap above plus the checkpoint invariant `observed != enforced`.

**G4 — an evidence family with no producer must be declared, not assumed.**
`provider.route` is exported, validated and tested but never emitted in production (T5).
*Proposal:* either wire it at the routing decision site, or mark it in the evidence contract as
**not currently produced** so no reader treats its absence as an absence of routing events.
*Traceable to:* T5, and to the invariant "missing or stale evidence cannot be reported as a successful
current control".

**Explicitly not proposed:** no new policy engine, no adapter SDK, no dashboard work, no schema-wide redesign,
no regulatory conformance claim (EU AI Act, ISO 42001) — the invariants forbid asserting those from evidence
alone, and this audit makes none.

## 6. Implementation dependency order

Ordered by dependency, not preference. Each step is blocked on the one above it.

1. **Correct the mis-describing comment** (`BoundaryEvidenceRecorder.kt:78-79`). Independent, trivial, no gate impact.
2. **Resolve `GovernedIdentity` carriage into approval creation paths** — already tracked against 0.7.1d/0.7.1e
   (`TASK-0.7.1e…:276-280`). 0.7.4b's identity work assumes a carried identity exists to reference.
3. **G1 — `PolicyContext` accepts the tuple.** Touches a public type; requires the API-compatibility and
   binary-compatibility gates. Must not be bundled with a gate or analyzer change.
4. **G2 — `source.component` becomes attributed and `enforcementStrength` is added**, with the
   derived-not-declared rule enforced at the emit path. Depends on 3 only for consistency of the identity the
   strength is reported against.
5. **G4 — declare or wire `provider.route`.**
6. **Freeze the 0.7.4b schema** only after 3–5 are demonstrable at a single tree, per the checkpoint's Exit clause.

Steps 1 and 2 are prerequisites, not part of 0.7.4b; step 4 is the only step that changes the evidence schema.
