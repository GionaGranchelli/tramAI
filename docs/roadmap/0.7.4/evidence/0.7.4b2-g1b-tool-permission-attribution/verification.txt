--- THE DIGEST DETERMINATION (added test first, red, then fixed, then green)
  Question: is the canonical workflowRunId cryptographically bound to the evidence?
  Test added before any production change:
      `the canonical payload digest binds the canonical run id`
      — two governed records, identical five deployment fields, identical decision and reason code,
        differing ONLY in the canonical run id.
  RED (before the change):  tests=9 skipped=0 failures=1 errors=0
      !! the canonical payload digest must bind the run of the evidence it describes
         ==> expected: not equal but was: <sha256:...
      Determination: the canonical payload digest did NOT bind the run id.
      Control in the same run: `legacy evidence keeps the digest it had before run-id binding existed`
      PASSED, so legacy digests were not the thing that changed.

  Change: computeToolPermissionPayloadDigest appends `workflowRunId` to the canonical payload ONLY when
  the record is attributed (attribution is atomic — zero reserved keys is legacy, a partial tuple is
  refused — so this is a binary state, not a heuristic). No new identifier, no schema version.

  GREEN (after the change): tests=9 skipped=0 failures=0 errors=0   BUILD SUCCESSFUL

  Why this was still worth doing although one digest already varied: `subjectDigest` is
  sha256(auditStreamId) and auditStreamId equals the run id only because DefaultAuditStreamIdResolver
  returns context.workflowRunId (AuditStreamIdResolver.kt:18-34). A deployment installing its own
  resolver keeps the stream and the run distinct, and the run id would then have been bound by nothing.
  The payload digest now binds it directly, independent of resolver configuration.

  Out of scope, reported not fixed: the governance.decision family
  (GovernanceDecisionEvidence.payloadDigest) has the same characteristic — its canonical payload does
  not include identity.runId. Changing it would re-digest that family's existing evidence.
