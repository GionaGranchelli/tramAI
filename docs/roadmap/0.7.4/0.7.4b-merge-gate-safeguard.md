# Merge-gate safeguard (process fix)

Status: implemented, not merged. Scope: the pre-merge verification gate only — no runtime code.

## The defect

A merge was performed through a gate whose query was invalid (`gh api … --json`, which `gh api` does
not accept). The query returned nothing. The gate looked for failing checks, found none, and reported
success. The merge itself was correct — but by luck of ordering, not because anything verified it. A
red pull request would have merged identically.

Remembering the mistake is not a safeguard. This is: the correction exists as an executable,
regression-tested gate in this repository.

## What the safeguard is

Three pieces, split so that the rules are testable without a network and the transport has exactly one
property to get right.

- **`build-logic/src/main/kotlin/dev/tramai/build/quality/MergeGateVerifier.kt`** — pure rules. Takes
  already-fetched evidence, performs no I/O, and reports violations instead of throwing, following the
  existing verifier idiom. The rules:

  | rule | refuses when |
  |---|---|
  | `head-unavailable` | the API reported no head — unavailable evidence is not a pass |
  | `head-mismatch` | the reported head is not the commit under review |
  | `checks-unavailable` | no status checks were read |
  | `check-not-successful` | any check is pending or unsuccessful |
  | `insufficient-successes` | fewer successes than the floor — an incomplete read is refused |
  | `workflow-runs-unavailable` | no workflow runs were read |
  | `required-workflow-missing` | a required workflow has no run at that commit |
  | `required-workflow-not-successful` | a required workflow is not completed/success |
  | `required-workflow-wrong-commit` | a required workflow ran at a different commit |
  | `check-names-unavailable` | required check identities were configured but no names were read |
  | `checks-inconsistent` | the rollup's names and states disagree in count |
  | `required-check-missing` | a required check identity is absent from the rollup |

  `checks-unavailable` is the rule the old gate lacked, and the regression test for it is the first
  test after the positive case.

- **`verifyMergeGate`** (registered by `TramaiReleaseVerificationPlugin`) — the transport. Its single
  property: **every** boundary failure collapses to empty evidence, which the rules refuse. `gh`
  absent, an invalid flag, a non-zero exit, an empty response — all produce no evidence, and no
  evidence is never a pass. `gh`'s stderr is surfaced so the next failure explains itself.

- **`scripts/verify-merge-gate.sh`** — how it is run, with `--self-check` asserting four refusals by their
  exact rule names *and* a positive control that a genuinely verified commit still passes. A gate that
  silently stops refusing — or silently stops passing — is the original defect in new costume.

## Evidence

`./gradlew :build-logic:test --tests '*MergeGateVerifierTest*'` — 24 tests, 0 failures. Positive case,
one negative per rule, `NEUTRAL`/`SKIPPED` accepted so the gate is not over-strict, and regressions for
every transport defect below. VERIFIED.

`./gradlew verifyMergeGate -PprNumber=518 -PexpectedHead=32d9a4ab…` — exit 0, "merge gate PASSED …
checks complete and green, required workflows successful". VERIFIED.

`./gradlew verifyMergeGate -PprNumber=518 -PexpectedHead=deadbeef…` — exit 1, refused with
`head-mismatch`, `workflow-runs-unavailable` and three `required-workflow-missing`. VERIFIED.

`./gradlew verifyMergeGate -PprNumber=999999 …` — exit 1, refused with `head-unavailable` and
`checks-unavailable`, i.e. the original defect live and refused. VERIFIED.

`./gradlew verifyMergeGate` with no properties — exit 1, refused. VERIFIED.

`./scripts/verify-merge-gate.sh --self-check` — `SELF-CHECK PASSED: four named refusals hold, and the
positive control still passes.` VERIFIED. Each refusal asserts its rule name (`checks-unavailable`,
`head-mismatch`, `required-check-missing`), so a compile failure or an unregistered task is a failed
self-check rather than a successful negative test.

`scripts/verify-merge-gate.sh 518 32d9a4ab… --merge` with `TRAMAI_MERGE_DRY_RUN=1` — shows the exact
merge call: `gh api --method PUT …/pulls/518/merge -f sha=32d9a4ab… -f merge_method=squash`. The `sha`
is GitHub's expected-head condition: had the head moved after verification, the call fails with 409
instead of merging an unreviewed commit. VERIFIED (dry run; this workflow does not perform the merge).

Suite at the corrected head: **29 tests, 0 failures**, spotless clean, no compilation errors. VERIFIED.

## Review corrections

1. **Verification was not bound to the merge** (time-of-check/time-of-use). Now `--merge` passes the
   reviewed SHA as GitHub's expected-head condition. Disclosed: the merges of #517 and #518 were performed
   *without* that condition, so they rested on a head check a push could have invalidated.
2. **The count floor did not prove coverage.** Replaced by `requiredCheckPrefixes` with
   `check-names-unavailable`, `checks-inconsistent` and `required-check-missing`; the floor is demoted to
   a documented sanity check and the overclaiming KDoc corrected.
3. **The self-check could report success on breakage.** Each negative asserts the specific rule name it
   expects, and a positive control was added: four expected failures are equally consistent with a gate
   that refuses everything.
4. **The suite is not enrolled in release-line CI.** Deferred to a separate `ci-workflow` PR, as
   `.github/AGENTS.md` rule 5 requires. Until then, green release-line CI does not establish that these
   tests ran.

## What running it for real found that the unit tests could not

All four defects below compiled cleanly and passed all 24 unit tests. They were reachable only by
executing the gate against real data. This is the distinction `AGENTS.md` draws: a verifier-level
discriminator cannot detect a missing registration at the call site.

1. **Defined but never registered.** `registerVerifyMergeGate` existed but was never called from
   `apply()`, so `verifyMergeGate` did not exist — *"Task 'verifyMergeGate' not found"*. A gate that
   does not exist cannot refuse.
2. **Trailing newline in `headRefOid`.** `gh` returns it with a newline, so an untrimmed comparison
   produced *"head moved from 32d9a4ab… to 32d9a4ab…"* — identical SHAs, spurious refusal. Now trimmed
   on both sides, with a regression test.
3. **Wrong jq path.** `gh pr view --json X --jq EXPR` applies `EXPR` to the whole response **object**,
   so the path must be `.statusCheckRollup[]`; `.[]` iterated the object's values and failed with
   *"expected an object but got: array"*, yielding no checks. `gh api` differs: it applies the
   expression to the body, which is why the workflow-runs query worked. Verified 18 states, all
   `SUCCESS`, matching the 18/18 rollup.
4. **Mixed casing between endpoints.** The Actions API returns `completed`/`success`; the status
   rollup returns `COMPLETED`/`SUCCESS`. The case-sensitive comparison rejected genuinely successful
   runs. Normalisation now happens once, at the parse boundary, with a regression test.

## Limits

- The gate cannot verify itself in CI at its own head: a pull request cannot be blocked by a check
  introduced within it. It is run locally before merging and by the person or agent merging; wiring it
  into CI is a separate `ci-workflow` change that would only protect *later* merges.
- It requires `gh`, authenticated, with access to the repository. Absent or unauthenticated, it
  refuses — correctly, but it cannot then verify anything.
- It reads the pull request's reported head. It does not establish that the reviewed *diff* is what
  the reviewer read; that remains a review-time obligation.
- `minSuccesses = 10` is a **sanity floor, not evidence completeness**. A partial response whose omitted
  entries were failures would satisfy it: ten successes from an eighteen-check set pass. Completeness is
  established by `requiredCheckPrefixes` — the required identities must be present — and a names/states
  count mismatch is refused as an inconsistent read. The floor remains because an empty or tiny read is
  still worth refusing outright.
- **The gate cannot verify itself at its own head**: a pull request cannot be blocked by a check
  introduced within it. The 29 regression tests are **not yet enrolled** in a release-line CI partition
  (the `ci.yml` contract-test partitions use explicit class filters, and `maintainability-baseline.yml`
  targets `master`). That enrollment is a `ci-workflow` change and therefore a separate PR under
  `.github/AGENTS.md` rule 5, with an exact test-count assertion. Until it lands, a green release-line
  CI run does **not** establish that these tests ran.
- **Merge authority is not delegated.** `--merge` binds the merge to the verified SHA, and the merge
  call is made by whoever holds merge authority — for `master` or `epic/**` that is the repository owner
  after reading the findings on the exact head. The script does not grant that authority; it removes the
  gap between a check and the use of that check.

## Proposed invariant for `AGENTS.md` (not applied)

`AGENTS.md` is protected in this workflow, so this is proposed for owner approval rather than written:

> **Merge gate.** A merge is authorised only by `scripts/verify-merge-gate.sh <pr> <head>`, which fails
> closed when the workflow and status data for that exact commit is unavailable, incomplete, pending,
> unsuccessful, or belongs to another commit. Green CI is necessary and never sufficient. A gate whose
> evidence could not be read must never report success.
