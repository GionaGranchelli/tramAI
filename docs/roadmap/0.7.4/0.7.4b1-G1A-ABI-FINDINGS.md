## 3. Method — exercised precompiled consumers, with a control

Reproducer and raw output: `evidence/0.7.4b1-bincompat/` (`Consumer.kt.txt`, `JavaConsumer.java.txt`, `probe2.sh`,
`report2.txt`, `candidate-governedRunIdentity.patch`). The consumer sources are stored with a `.txt` suffix because
the repository's static gates scope by changed file, and they are evidence rather than compilable module source.

**Replay, from committed files only.** Nothing depends on a local path or on a working-tree edit:

```bash
# TRAMAI_REPO points at any clone of this repository; the default is the current directory's checkout.
TRAMAI_REPO=/path/to/tramai clone \
  bash docs/roadmap/0.7.4/evidence/0.7.4b1-bincompat/probe2.sh
```

The script creates its own throwaway worktree at the base revision, applies
`candidate-governedRunIdentity.patch` **into that worktree**, compiles the consumers against the base artifact, and
runs the same class files against both jars. The caller's checkout is never modified — the candidate is supplied as a
patch rather than as an uncommitted edit, so the evidence is reproducible by anyone holding this branch.

The patch is a single trailing defaulted property, which is the compatibility-favourable placement.

`report-replay.txt` is the output of a full `probe2.sh` run on a different machine path (`/tmp/bincompat2.*`) than
the original `report2.txt`. It reproduces the same outcomes — control 10/10 Kotlin and 4/4 Java OK against the base
jar; candidate 6 Kotlin failures on the synthetic `<init>`, the `copy(16-arg)` descriptor gone, `component16`
present, Java 4/4 OK — so the reproducer is demonstrated rather than asserted.

1. A base worktree is created at `6e1d4a1e` and its `:tramai-core:jar` built.
2. The consumers are compiled **against that base artifact** — Kotlin through `:tramai-core:compileTestKotlin`,
   Java through `javac` against the base jar. Their `.class` files are kept.
3. Those exact class files are run against the **base** jar (control) and then against a jar built from a tree

The candidate, per the audit's design, was appended **last** so that every existing `@JvmOverloads` descriptor and

## 5. Two independent mechanisms — and why the design cannot avoid them

1. **The synthetic default-arguments constructor.** Any Kotlin call site that omits any argument — which includes
   every call using named arguments — links against this synthetic descriptor. Adding a property regenerates it,
   so the old descriptor disappears and **every such call site fails to link**. This is broader than the risk the
   task anticipated: it is not limited to `copy`.
2. **`copy` and `copy$default`.** Kotlin generates these across all properties, so their descriptors change
   whenever a property is added.

Both are produced by the Kotlin compiler from the property set itself. **No property-addition design to a public
data class can preserve both descriptors**, which is why §9's instruction to find "the smallest additive, immutable
alternative that retains the canonical type" has no solution inside the current contract:

- dropping `data` would remove `copy`/`componentN` — forbidden by the task and a far larger break;
- a hand-written `copy` cannot keep the old descriptor while also covering the new property;
- an immutable carrier elsewhere in the type does not help, because the type must hold the identity for the
  evaluator to receive it.

Java consumers are unaffected, which is worth recording: the break is Kotlin-specific and linkage-level, invisible
to any rebuild-based check. A change that compiles cleanly for every in-repo consumer still breaks every Kotlin
consumer compiled against the previous artifact.

## 6. Alternatives for owner decision

| # | Design | ABI impact | Tradeoff |
|---|---|---|---|
| A | Reserved key in the existing `attributes: Map<String, String>`, validated atomically, with a typed reader in a **non-stable** module | **none** — no descriptor changes | identity is stringly-typed at the context boundary; the evaluator receives a map, not the canonical type; validation must be fail-closed and must reuse the 0.7.1d discipline rather than invent a second representation |
| B | A separate typed carrier on a new evaluation entry point in a new or non-stable module | none for `tramai-core` | a second evaluator input, which the checkpoint's "one authoritative evaluator" invariant makes risky; larger surface than the problem |
| C | Ship the trailing defaulted property on the next release line, where a stable-API change is sanctioned | the break above, accepted deliberately | the design is otherwise correct (additive `componentN`, Java-safe) and needs only a sanctioned transition; it cannot be done on the 0.7.x line |
| D | Reclassify `:tramai-core`'s `apiStability` | permits A/B/C | outside this task's authority, and it is a policy change to the gate being satisfied — an owner decision, never an agent one |

**Recommendation:** A for the 0.7.4b sequence (it is the only option that changes no ABI), with C as the durable
fix for the next line, and **D explicitly not taken by an agent**.

## 7. Next discriminating experiment

The mechanism is settled for `stable` modules; two questions remain open and each has a cheap decisive test:

1. **Does the sanctioned `preview` path work for exactly this change?** Add the same field to a `preview` module
   and confirm the `api-migrations.yml` entry authorises the transition. If it does, the migration mechanism is
   viable for 0.7.4b3 (G2), whose target types live in preview modules — which materially changes that task's plan.
2. **Does option A carry identity end to end without a new authority?** Implement the reserved-key validation in the
   evaluator's own module and prove, with the XR1 boundary, that a governed invocation reaches `PolicyEngine.evaluate`
   with an identity that is validated, not merely present — and that a partial or mismatched identity is refused
   rather than normalised.

## 10. What was not done, and why

- **No production code change.** The candidate field was reverted after measurement. A known-broken public API
  change is not a partial delivery.
- **No gate, baseline, API-dump or workflow change**, and no `api-migrations.yml` entry was added. Adding one to
  authorise this transition would be a fabricated migration history authorising itself, which is precisely what the
  owner's Socratic clause on the verifier forbids.
- **G1b, G2, G4 and the evidence-schema work were not started.**
- The XR1 boundary, its tests, and all existing policy semantics are untouched.
