# 0.7.4b5 — Merge-gate RC applicability correction

Status: in review.
Base: `2c7e3206f271a86e525c37be21a06da4b6fa8288` (`release/0.7.0`).
Change class: `build-logic` (plus the CI lane's pinned counts in `.github/workflows/ci.yml`, which the gate fix
requires and which itself makes this change RC-relevant).

## The defect

`verifyMergeGate` demanded the `Sovereign Runtime Release Candidate` workflow run and its `validate` job on
**every** pull request, while that workflow's own `pull_request.paths:` filter excludes ordinary documentation.
A documentation-only pull request therefore could not satisfy the gate at any head:

```
> merge gate REFUSED at b0faecee: 2 violation(s)
    - [required-check-missing] 1 required check(s) absent from the rollup: validate
    - [required-workflow-missing] 'Sovereign Runtime Release Candidate' has no workflow run at b0faecee
```

Verified at the source: `MergeGateTask` listed all three workflows in `requiredWorkflows`, `validate` sat in the
unconditional `REQUIRED_CHECK_IDENTITIES`, and `MergeGateVerifier`'s required-workflow rule has no path branch —
only `conditionalChecks` had path applicability, and its single entry covered the mutation workflow. Observed on
PR #525 (a five-file documentation change whose only other runs were `CI` and `Architecture Authority`).

This is the same class of false refusal the gate's own record already documents for the mutation workflow
(`0.7.4b-merge-gate-safeguard.md`, "Superseded, recorded rather than erased"): a required set copied from one
green rollup records what ran on one pull request, not the contract for every pull request.

## The correction

1. **`validate` moves from unconditional to path-conditional.** It left `REQUIRED_CHECK_IDENTITIES` and is
   required through `CONDITIONAL_CHECKS`, keyed by the RC workflow's filters.
2. **`Sovereign Runtime Release Candidate` becomes a path-conditional required workflow.** `Evidence` gains
   `conditionalWorkflows` (workflow name → the filters that workflow declares), and the run-level rules are
   decided by the same applicability rule the check-level rules already use.
3. **The filters are read from the producing workflow, not transcribed.**
   `pullRequestPathFilters()` (in `build-logic/.../quality/MergeGatePathFilters.kt`, split out because
   `MergeGateVerifier.kt` sits at its function-count limit and this is a distinct concern) parses
   `on.pull_request.paths` out of `.github/workflows/sovereign-runtime-release-candidate.yml`. A copy in the
   gate would drift the moment that workflow's `paths:` change, and a drifted copy fails in both directions: it
   demands a run that legitimately did not happen, or stops demanding one that should have. Reading keeps the
   authority with the workflow.
4. **Fail closed on unusable filters.** Text with no parsable `pull_request.paths` yields a match-everything
   filter, so an unreadable or reshaped workflow file makes the requirement unconditional — a refusal — rather
   than inapplicable, which would be a silent pass. The file read follows the gate's existing convention: any
   failure collapses to empty evidence, and empty evidence is refused.
5. **The `paths:` sequence closes at a key line, not at an indentation threshold.** A first cut collected
   every deeper line. That reads a *sibling* key's own items as paths: `branches:` sits at exactly `paths:`'s
   indentation and its items are indented just as deep, so `branches` entries became path filters and the gate
   demanded an RC run for pull requests GitHub never triggered it for — the same false-refusal class this
   correction exists to remove. `keepsPathsSequenceOpen()` now continues only for items of the sequence
   (intervening blank and comment lines allowed, as the real workflow has one) and stops at the first key line.
   A regression test pins it, with the sibling-key fixture the finding used.

## What is preserved

- `CI` and `Architecture Authority` remain required on every pull request, unconditionally.
- The mutation workflow's applicability entry is unchanged.
- A **conditional** requirement is demanded, then judged, exactly as before: missing, not
  `COMPLETED/SUCCESS`, or present at another commit each refuse.
- Unread changed paths still refuse (`changed-paths-unavailable`), and a path list shorter than GitHub's own
  changed-file count still refuses (`changed-paths-incomplete`). Undecidable applicability is now demanded *as
  well* by the run-level rule, so the workflow rules no longer depend on a refusal raised elsewhere.
- A conditional workflow whose filters match, with its run absent, wrong-commit or unsuccessful, is refused —
  the negative tests cover each.

## Tests

`build-logic/src/test/kotlin/dev/tramai/build/quality/MergeGateVerifierTest.kt` — added to the class already
enrolled in the `ci-wiring` contract lane (no new lane, no new required check identity):

- a documentation-only change does not require the RC workflow (the positive case the defect made impossible);
- a change matching the RC filters requires the RC workflow;
- a change matching the RC filters requires the `validate` check;
- `validate` must have succeeded (a SKIPPED `validate` is refused);
- an RC run at another commit does not satisfy the requirement;
- a pending RC run is refused;
- conditional workflows configured with unread paths is refused, and the run is demanded as well;
- a truncated path list leaves conditional workflows demanded;
- the path filters are read from the workflow's own YAML (with `push:` filters proven not to be mistaken for
  `pull_request:` ones);
- **a sibling key after the `paths:` sequence does not extend it** — the regression test for the finding: the
  fixture's `branches:` entry must not become a path filter;
- **the real RC workflow's own filters decide the RC requirement** — a wiring test that reads
  `.github/workflows/sovereign-runtime-release-candidate.yml` as committed, requires the RC workflow for an
  analyzer path under the filters read from it, and requires nothing for
  `docs/evidence/runtime-evidence-export-model.md`;
- workflow text without parsable paths falls back to matching every path (the fail-closed direction).

The sibling-key test discriminates, and here is the transcript rather than the assertion that it does — the
predicate was reverted to the indentation-only shape, the class re-run, and the parser restored byte-identical
(`sha256` equal) before the control run:

```
mutated (indentation only): tests=51 failures=1
  FAILED: a sibling key after the paths sequence does not extend it()
restored: byte-identical
control (as committed):     tests=51 failures=0 errors=0
```

The lane's pinned counts in `.github/workflows/ci.yml` are updated from the measured report, not from
arithmetic: the non-vacuity check reads this class's own XML and holds it to an exact test count, so a
selection that runs zero of them cannot pass. Measured under the JDK 25 the lane uses, both classes selected,
fresh results (`--rerun-tasks --no-build-cache`): `MergeGateVerifierTest` **51 tests, 0 failures, 0 errors,
0 skipped**; `TestsWatchdogWiringTest` 6; lane total **57** (was 38 and 44 at the base).

The lane run is also the evidence that the correction keeps the existing contract: the 38 pre-existing tests
still pass, including one whose hard-coded run count had to follow the required set instead of the literal
three it asserted.

## Evidence for the corrected applicability

At the head that first exposed the defect, the gate refused with exactly the two rows the fix targets:

```
> merge gate REFUSED at b0faecee: 2 violation(s)
    - [required-check-missing] 1 required check(s) absent from the rollup: validate
    - [required-workflow-missing] 'Sovereign Runtime Release Candidate' has no workflow run at b0faecee
```

The positive case is the new unit test (`a documentation-only change does not require the RC workflow`), and the
live confirmation on a documentation-only pull request is the re-run recorded in that pull request's review
thread: same command, same head, no missing RC requirement.

## Non-claims

- No `docs/**` entry was added to the RC workflow. Release certification is not run for unrelated documentation;
  the gate was corrected instead.
- No manual merge exception, no `-PrequiredChecks` change, no required check dropped from a configuration that
  needs it: every identity that was required on an RC-relevant pull request is still required there.
- The gate is not weakened for RC-relevant changes: they require the same workflow and the same job as before,
  and now the check-level and run-level rules are decided by one rule instead of two.
- This document does not certify PR #525; that pull request is re-verified against the repaired gate at its own
  head.
