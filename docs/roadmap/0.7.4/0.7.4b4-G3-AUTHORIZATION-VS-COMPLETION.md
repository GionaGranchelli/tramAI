Status: delivered, awaiting review.
Source revision inspected: `2c7e3206f271a86e525c37be21a06da4b6fa8288` (`release/0.7.0` after G2 / PR #523).
Prerequisite: G2 / PR #523, merged as `2c7e3206`.
Change class: documentation. No production behaviour, serialization, public API or runtime schema is changed.

## The contract

**An ALLOW record proves authorization, not successful execution.**

That is the complete statement. `tool.permission` evidence attests the policy engine's **authorization decision** at
one enforcement point. It does not attest that the operation started, completed, succeeded or changed external
state, and the absence of completion evidence must not be read as either outcome.

Three facts are kept apart, and only the first one is evidential:

| Fact | What it is | Attested by `tool.permission`? |
|---|---|---|
| Policy decision | What the engine authorized or refused at the named enforcement point | **Yes** — this is the record's content |
| Enforcement contract | What a particular governed boundary is designed and tested to prevent | No — it is a property of that boundary and its tests |
| Execution completion | Whether the operation ran, and what it returned | **No** — in either direction |

Per decision kind:

- `ALLOW` — the policy engine authorized the operation at the specified enforcement point. Not proof that
  execution started, completed or succeeded.
- `DENY` — the policy engine refused permission at the specified enforcement point. The decision record alone is
  not proof about every possible execution path outside the governed boundary.
- `REQUIRE_APPROVAL` — the policy engine required approval. The record is not evidence that approval was
  subsequently granted or that execution resumed.

## G3.1 — the ordering this contract is traceable to

Read from the source at `2c7e3206`, not inferred from method names or test descriptions.

**Path 1 — the declared XR1 boundary** (`examples/spring-ai-authority-boundary`):

```
GovernedToolCallback.govern                                    :55-102
  engine.evaluate(contextFor(toolName))                        :65-66
  PolicyDecision.Allow -> {                                    :79
      recorder.recordAllow(toolName)                           :83   ← authorization recorded, awaited
      execute(toolInput)                                       :84   ← delegate invoked only after the write
  }
BoundaryEvidenceRecorder.recordAllow                           :55
  -> record(toolName, DECISION_ALLOW, reasonCode = null)       :76-116
      -> auditEngine.emit(AuditEmission(...))                  :83   (inside runBlocking)
      -> events += returned event                              :115
AuditEngine.emit                                               :11-34
  -> store.appendNext(streamId) { factory }                    :12   the store owns the write and the sequence
  -> returns the persisted AuditEvent                          :32
```

`emit` is a suspend function that returns only after the store has accepted the append, and `recordAllow` is
called on the line before `execute`. **The ALLOW audit write therefore completes before the delegate is
invoked.** VERIFIED by reading the ordering, and independently discriminated by an existing test (below).

Consequences, each a property of that ordering:

- a successful delegate execution leaves an ALLOW record;
- a delegate that throws or fails after authorization **also** leaves an ALLOW record;
- the presence of the ALLOW record does not distinguish those outcomes;
- the absence of completion evidence is not evidence of success, and not evidence of failure.

The design reason is stated in the code itself (`GovernedToolCallback:80-82`): if the audit store cannot accept the
decision, the action must not run at all. Recording first is what makes the *failed write* stop the effect.

**Path 2 — the native engine tool path** (`tramai-engine`):

```
ToolInvocationExecutor.execute                                 :21-55
  repeat(maxAttempts) {                                        :27
      authorizationCoordinator.authorize(request, input)       :36
      -> ToolAuthorizationCoordinator.authorize                :10-22
         -> PolicyEnforcementHelper.evaluate                   :39-44
            -> policyEngine.evaluate(context)                  :41
            -> auditEmitter.emit(enforcementPoint, ctx, dec)   :42   ← decision recorded here
            -> returns the decision to the caller              :43
      executeToolAttempt(tool, input, context)                 :41 / :57-58   ← tool.execute(...)
  }
```

Same ordering, same consequence: the decision audit is emitted inside `evaluate`, before `executeToolAttempt` runs.
`AuditEnginePolicyDecisionAuditEmitter.emit` (`:48-77`) does not swallow a store failure, so a failed write
propagates out of `authorize` and the tool is never invoked.

One difference worth recording, because it is another reason no reader may treat ALLOW records as completions:
the authorization is evaluated **once per attempt** (`:27`, `:36`), while the operation completes at most once.
Attempts, authorization records and completions are not 1:1 in this path.

**The ordering discriminator that already exists in the repository.**
`EvidenceIntegrityTest.a failure to record the authorization prevents the action` (`:104-119`) wires a store that
cannot accept the write, asserts that the call fails, and asserts that the guarded ledger — the observable side
effect — is **empty**. If the effect preceded the record, the ledger would be non-empty and the test would fail.
That is a genuine discriminator for the ordering, and it also establishes the fail-closed intent.

## G3.2 — normative semantics in the evidence model

Documented in `docs/evidence/runtime-evidence-export-model.md`, family D (`tool.permission`), in the new
subsection **"What a `tool.permission` decision attests — and what it does not"**:

- the per-decision attests/does-not-attest table for `ALLOW`, `DENY` and `REQUIRE_APPROVAL`;
- the three facts kept apart (policy decision, enforcement contract, execution completion);
- the pre-effect recording rule and its consequence, stated as a reader restriction;
- the reserved-metadata scope (`identity.*`, `boundary.id` / `boundary.enforcementStrength`) with **G2's
  limitation retained**: a producer-declared boundary identifier and its registered strength do not independently
  verify the event's origin.

It is restated in the document's own claim boundary: "What the Verifier Must NOT Claim" gains the
ALLOW-proves-completion item (in both directions), and Non-Claims gains the matching entry. Both lists previously
said nothing about completion at all.

## G3.3 — developer guide alignment

Documented in `docs/guides/governed-tool-use.md` in the new section **"What an ALLOW Record Means — Authorization,
Not Completion"**:

- the example's invocation counters describe what happened **in that example's process** — a property of that run,
  not of the evidence — and do not turn an `ALLOW` record into a general-purpose completion certificate;
- the worked sequence:

  ```
  Policy decision:             ALLOW
  Audit emission:              successful
  Delegate invocation:         attempted
  Delegate result:             exception
  Result: ALLOW evidence is valid. Successful execution is not established.
  ```

- recording the authorization before the delegate runs is **intentional** (a failed authorization write must
  prevent delegation);
- the example's "does not demonstrate" list gains the completion non-claim.

No ALLOW/DENY/REQUIRE_APPROVAL behaviour is changed, and the guide adds no decision kind.

## Explicit non-claims

- No new evidence mechanism, and no completion authority: no `tool.completed` event, no execution-success or
  failure evidence, no completion ledger, no post-execution attestation, no additional policy decision, no new
  schema field.
- No change to `AuditEngine`, exporters, `RuntimeEvidenceContractValidator`, `RuntimeEvidenceBundleWriter`,
  bundle verification, event-origin authentication, provider-routing evidence, dashboards or adapters.
- No claim that the XR1 demonstration's invocation ledger is a production completion authority. It shows
  execution **inside that demonstration** and nothing more.
- No claim that the example's counters generalise to any other wiring.
- The G1/G2 findings in `0.7.4a-GOVERNANCE-EVIDENCE-AUDIT.md` and `0.7.4b3-G2-…md` are not rewritten: this task
  records only what G3 documents.

## Remaining gaps

1. **No committed discriminator for the reverse direction.** The observation above is transient. A test-only
   follow-up could pin it in `examples/spring-ai-authority-boundary` (a throwing delegate must still yield a valid
   `ALLOW` record). It is a separate concern from the contract's documentation, which is why it is not in this
   documentation-only change.
2. **Execution-completion attestation does not exist and is not proposed.** If a future task wanted it, it would
   have to be a new evidence capability with its own authority question — explicitly out of G3's scope.
3. **Event-origin authentication of a declared boundary identifier remains unverified** (G2, unchanged): the
   identifier is producer-declared and its registration strength does not authenticate the emitter.
