# 0.7.4b3 / G2 — Registered Enforcement Boundary Provenance

Status: in progress (names frozen before implementation, per the G2 directive).
Base: `7c823d05d47d6322802a894257cbcae49f4eb36c` (`release/0.7.0` after G1b / PR #521).

## Goal

Make `tool.permission` evidence able to state **which declared execution boundary enforced the
decision** and **what enforcement strength that boundary is entitled to claim** — without letting an
integration promote itself.

G1a/G1b established *what was decided* and *under which governed identity*. G2 adds the separate fact
of *who enforced it, provably, and how strongly*.

## The distinction this slice exists to protect

- **Authorization** — TramAI's policy engine decided ALLOW / DENY / REQUIRE_APPROVAL. Producer of the
  record: the engine. `source.component` therefore stays the constant `"policy-engine"`.
- **Enforcement** — a specific declared execution boundary prevented or permitted the action.

These are different facts. `source.component` identifies the decision producer and must not be
repurposed to name the boundary: it is pinned in three coupled places (the exporter writes it,
`RuntimeEvidenceBundleWriter.EXPECTED_SOURCE_COMPONENTS` permits it, and
`RuntimeEvidenceContractValidator.validateSourceComponent()` rejects any mismatch), and
`computeToolPermissionPayloadDigest()` folds it into every payload digest. Making it configurable would
be both rejected and digest-breaking — see the withdrawn W1 in the 0.7.4a audit.

## Frozen vocabulary

Reserved metadata keys, `tool.permission` family only (this slice adds no provenance to any other
family for symmetry):

- `boundary.id` — the stable declared boundary identifier.
- `boundary.enforcementStrength` — the strength value, **framework-derived** (see below).

Enforcement strength vocabulary, frozen here from the XR1 checkpoint's four concepts (whose names were
explicitly deferred to this work):

- `AUTHORITATIVE` — the boundary consults the policy engine before delegating and prevents execution
  when the decision is DENY, when human approval is required, and when governance is unavailable.
- `INSTRUMENTED` — the boundary participates but its prevention is not proven.
- `OBSERVED` — the boundary records only; nothing is prevented.
- `IMPORTED` — the boundary's evidence was imported from outside this runtime.

This slice registers exactly one boundary at `AUTHORITATIVE`. The other three values are defined so the
ceiling rule is expressible and testable, not because a producer exists for them.

### The registered boundary

| field | value |
|---|---|
| `boundary.id` | `spring-ai-tool-callback` |
| applicable enforcement point | `BEFORE_TOOL_EXECUTION` |
| granted strength | `AUTHORITATIVE` |
| declared contract | consults `PolicyEngine` before delegating; prevents the delegate when the decision is DENY, when human approval is required, or when governance is unavailable |
| prevention evidence | `GovernanceBoundaryTest`: a denied action is never invoked · an action requiring approval cannot execute without one · an unavailable authority prevents execution |

Registration lives in `tramai-security` (`RuntimeBoundaryProvenance`), not in the example: an
adapter-owned table would be exactly the self-registration this slice forbids.

### The one pre-existing self-asserted strength, and what happened to it

`BoundaryRefusal.enforcementStrength` already existed in the example module, **defaulted to
`AUTHORITATIVE`** — an integration declaring itself authoritative, which is the invariant this slice
protects. It has no test dependents. The default was removed, so the value is explicit at its single
construction site.

**Non-claim:** that field is the boundary's caller-facing refusal payload, not evidence. It stays
boundary-declared, and is pinned to the framework-resolved value by `GovernanceBoundaryTest`, so the two
cannot silently diverge. The authority for enforcement strength is the registration; the refusal payload
is a convenience that a caller must not read as an independent attestation.


## Trust model — strength is derived, never asserted

The central invariant: **an integration cannot claim AUTHORITATIVE enforcement merely by declaring
itself authoritative.**

- Strength is a property of a **framework-owned registration**, not of caller metadata. Resolution
  happens inside `tramai-security`; the producing boundary supplies only its declared `boundary.id`.
- A caller-supplied `boundary.enforcementStrength` is **refused**, not silently overwritten: accepting
  it would make the field a self-asserted claim, and ignoring it would hide an attempt to make one.
- An **unregistered** `boundary.id` is refused. A registered boundary may never exceed the strength its
  registration grants, so registration is what makes AUTHORITATIVE reachable — and unreachable from
  outside the framework.
- The registered boundary's declared **enforcement point** must match the enforcement point the record
  actually carries (`metadata.enforcementPoint`, an existing tool.permission key). A mismatch is
  contradictory provenance and is refused.

The registered entry associates the four things G2.1 requires: the stable identifier, its applicable
enforcement point, its verified enforcement contract, and the maximum strength that contract supports.
The AUTHORITATIVE claim is narrowly scoped to the declared Spring AI `GovernedToolCallback` at
`BEFORE_TOOL_EXECUTION`: it proves prevention **at that boundary**, and asserts nothing about any other
application execution path.

## Evidence rules

- **Atomicity, mirrors identity:** zero provenance keys is valid legacy evidence; a partial pair is
  corruption and is refused; a complete pair must be registered, applicable and within ceiling.
- **Fail closed, never downgrade:** a malformed record that claims provenance is refused. It is never
  re-read as successful legacy evidence.
- **Digest participation:** provenance is assembled **before** the canonical payload digest is
  computed, exactly as the reserved `identity.*` keys are. Changing `boundary.id` or the resolved
  strength must change the payload digest of a provenance-bearing record.
- **Legacy compatibility:** a record with no provenance keys gains no digest term, so existing digests
  stay byte-identical. Attribution is atomic, so this is a binary state, not a heuristic.
- **Unchanged:** `RuntimeEvidenceRecord`, the public `runtime-evidence.v1` schema version, the
  `source.component` contract, and the five `identity.*` keys with `workflowRunId`.
- **Reviewer parity:** `examples/sovereign-lab/verify-evidence-bundle.sh` must accept and validate the
  same semantics, so a bundle the JVM contract accepts is not rejected for carrying valid provenance.
  The family allowlists are broadened only by this provenance extension.

## What a registered contract does and does not prove

A registered boundary contract plus its prevention tests is **not** cryptographic authentication of an
arbitrary external caller. Strength attests that a framework-registered boundary is documented and
tested to prevent execution at one declared enforcement point. Any process able to reach the boundary
can attempt a call; stronger workload identity authentication remains a separate, unresolved security
concern (tracked as G2-adjacent work, not solved here).

Separately: **an ALLOW record proves authorization, not successful completion.** The boundary records
ALLOW before the effect, so nothing in this evidence attests that the delegate then succeeded.

## Required adversarial evidence

- Positive: the real Spring AI callback through the real policy evaluator and the real audit/evidence
  chain (pure registry tests are necessary but not sufficient).
- D1 remove trusted provenance binding → real-boundary positives fail.
- D2 bypass the strength-registration check → the unregistered/over-claimed AUTHORITATIVE negative
  discriminator fails.
- D3 remove provenance from the canonical digest input → digest-binding tests fail.
- D4 remove the shell verifier's provenance support → the finalized attributed bundle is rejected while
  the legacy control still passes.
Each discriminator is recorded as control → mutation → restoration, with the task proven to have
actually executed: a compilation error or a Gradle cache hit is not a successful negative test.
